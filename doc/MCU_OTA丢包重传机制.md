

# SOC 侧 OTA 丢包重传配合说明

> 面向 SOC / 上位机开发。帧格式、TLV 编号、Flash 分区等基础定义以
> 《MCU串口通信协议文档.md》"OTA 升级（A/B 双槽，CMD/TLV 四阶段）"一节为准，
> 本文只讲 **SOC 在每一步要等什么、等多久、没等到怎么办**。
> 对应 MCU 固件：`MainBoard_MCU_APP_V4`（`ota_task_app.c`），BOOT：`MainBoard_MCU_Boot_V4`。

---

## 0. 一句话结论

**OTA 全程是停等协议（stop-and-wait），SOC 是唯一的重传发起方。**
MCU 永远不会主动说"你那一包我没收到"——它没有 NAK 帧，坏帧直接静默丢弃。
SOC 每发一帧，只做三件事：**等对应的业务应答 → 超时或应答为 0 就用同一个 Seq 原样重发 → 应答为 1 才发下一帧**。

---

## 1. 必须先知道的 5 条 MCU 行为

| #    | MCU 行为                                                     | 对 SOC 的含义                                                |
| ---- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 1    | 通信层收到校验和错 / 长度错 / 帧头错的帧，**静默丢弃**，不回任何东西 | 线上坏帧 = 无应答，只能靠 SOC 超时发现                       |
| 2    | 每一帧合法的 `0xAA` 请求，通信层**先**回一帧 `0xBA`（Port/Cmd/Seq 相同，Payload 回显首 TLV Type、Len=0），**然后**才转给 OTA 任务处理并回 `0xBB` 业务应答 | 每发一帧会收到**两个**回复：`0xBA` 只表示"帧收到了"，**判断能否发下一包必须看 `0xBB`**，`0xBA` 可以忽略 |
| 3    | 数据包按 Seq 严格顺序写入：`Seq == 期望值` 才写并回 `PACKS_ACK=1`；**最近一次成功的 Seq 再来一次，只补回 ACK=1、不重复写 Flash**；其它 Seq 一律回 `PACKS_ACK=0` 且不推进 | 同 Seq 重发是安全的、幂等的；但 SOC **不能跳包、不能回退两包以上** |
| 4    | 会话空闲超时 **5 秒**（`OTA_SESSION_TIMEOUT_MS`）：READY / ACTIVE 状态下 5 秒没收到任何合法 OTA 帧，MCU 判本次升级失败，元数据置 FAILED、回到 IDLE | SOC 相邻两帧（含重发）之间的总耗时必须远小于 5 秒；一旦超时只能从阶段一重来 |
| 5    | 首包判定通过前 MCU 要擦除候选槽 2×128KB，STM32F407 单 Bank，**擦除期间 CPU 完全停摆最长约 8 秒**，串口帧不会被处理 | 首包应答要放宽等待（建议 90 秒），**擦除期间不要发任何帧**（发了也会丢） |

## 2. 四个阶段各自的"等 / 超时 / 重发"规则

帧示例中 `[CS]` = 从 `5A` 到 Payload 末字节累加和的低 8 位。

### 阶段一：OTA 请求（Port `0xA2` / Cmd `0x30`）

| 项目       | 内容                                                         |
| ---------- | ------------------------------------------------------------ |
| SOC 发     | `5A A5 AA A2 30 [Seq] 02 01 00 [CS]`（`TLV_OTA_REQ`=0x01, len=0）。例：Seq=0 → `5A A5 AA A2 30 00 02 01 00 7E` |
| 等待的应答 | `0xBB` + `TLV_OTA_REQ_RESULT`(0x02, len=1)：`5A A5 BB A2 30 [Seq] 03 02 01 [0/1] [CS]`。例：允许 → `5A A5 BB A2 30 00 03 02 01 01 93` |
| 超时       | **1 秒**                                                     |
| 超时动作   | 同 Seq 重发，最多 **3 次**；仍无应答 → 判"MCU 无响应"，终止并提示 |
| 应答 = 0   | MCU 拒绝（正在打印 / 上一次 OTA 的试运行自检尚未出结论）。**不是丢包**，不要立刻重发；等待 ≥ 3 秒或提示用户后再试 |
| 应答 = 1   | MCU 进入 READY，**5 秒内必须发出首包**，否则 MCU 自动回 IDLE，需重新走阶段一 |

### 阶段二 A：首包 Seq=0（Port `0xA6` / Cmd `0x31`）

| 项目       | 内容                                                         |
| ---------- | ------------------------------------------------------------ |
| SOC 发     | `5A A5 AA A6 31 00 82 01 80 [128 字节元数据] [CS]`，Value 前 16 字节 = write_slot(4) + firmware_len(4) + crc32(4) + fw_version(4)，小端，其余 0xFF |
| 等待的应答 | `0xBB` + `TLV_OTA_JUDGMENT_SEQ`(0x02, len=1)：通过 `5A A5 BB A6 31 00 03 02 01 01 98`；拒绝 `5A A5 BB A6 31 00 03 02 01 00 97` |
| 超时       | **90 秒**（正常 1~8 秒内返回，8 秒是擦除上限）               |
| 等待期间   | **静默**：不发任何 OTA 帧，也不发版本查询、心跳等其它命令    |
| 超时动作   | 此时 MCU 状态未知（可能擦除中、可能已 5 秒超时回 IDLE）。**不要重发首包**，回到阶段一重新请求；若阶段一应答 = 1 再发首包 |
| 应答 = 0   | 参数不合法或"目标槽 = 当前运行槽"。MCU 仍停在 READY。**不重复阶段一**，在 5 秒内直接发**另一个槽**镜像的 Seq=0 首包（SOC 应同时持有 A、B 两个槽的包） |
| 应答 = 1   | 进入数据传输，从 Seq=1 开始                                  |

### 阶段二 B：数据包 Seq ≥ 1

| 项目                  | 内容                                                         |
| --------------------- | ------------------------------------------------------------ |
| SOC 发                | `5A A5 AA A6 31 [Seq] [Len+2] 01 [Len] [Len 字节数据] [CS]`。中间包 Len=0x80、帧 Len=0x82、整帧 138 字节；**尾包 Len = 剩余实际字节数**（4 字节对齐），帧 Len = 实际长度 + 2 |
| Seq 规则              | `Seq = 包序号 & 0xFF`，首包 0，数据包 1、2、3 … 255、0、1 …循环。一个 150KB 镜像约 1200 包，会循环 4~5 轮，MCU 侧同样按 8 位比较 |
| 等待的应答            | `0xBB` + `TLV_OTA_PACKS_ACK`(0x03, len=1)，**Seq 必须与刚发的包一致**：成功 `5A A5 BB A6 31 [Seq] 03 03 01 01 [CS]`（Seq=1 时 CS=9A）；失败 `... 03 03 01 00 [CS]`（Seq=1 时 CS=99） |
| 超时                  | **500 毫秒**（正常 10~30 ms 内返回）                         |
| 超时动作              | 同 Seq 原样重发，最多 **5 次**（5×0.5 s = 2.5 s < 5 s 会话超时）。仍无应答 → 判链路故障，终止本次升级，**等待 ≥ 6 秒**让 MCU 会话超时回 IDLE 后，从阶段一重来 |
| 应答 = 0              | 立即（或延迟 20~50 ms）同 Seq 重发，计入上述 5 次；连续 5 次 = 0 → 终止，同上 |
| 应答 = 1              | 发下一包                                                     |
| 收到 Seq 不匹配的 ACK | 迟到的旧 ACK，**忽略**，继续等当前 Seq                       |
| 收到 `0xBA`           | 通信层确认，**忽略**                                         |

### 阶段三：完成通知

| 项目       | 内容                                                         |
| ---------- | ------------------------------------------------------------ |
| SOC 发     | `5A A5 AA A6 31 [Seq] 02 04 00 [CS]`（`TLV_OTA_FINISHED`=0x04, len=0）。例：Seq=0 → `5A A5 AA A6 31 00 02 04 00 86` |
| 等待的应答 | `0xBB` + `TLV_OTA_FINISHED_ACK`(0x05, len=1)，Seq 与请求一致：成功 `5A A5 BB A6 31 00 03 05 01 01 9B` |
| 超时       | **2 秒**（MCU 要做整槽 CRC32，通常 < 200 ms）                |
| 超时动作   | 同 Seq 重发，最多 **3 次**。注意：若 MCU 已回 ACK=1 但该帧丢失，MCU 会在 300 ms 后**复位**，重发的 FINISHED 不会再有任何应答，串口上随后出现 BOOT 的 ASCII 横幅。因此 **3 次重发都无应答时不要判失败，直接进入阶段四轮询**，由版本查询结果定成败 |
| 应答 = 0   | 长度或 CRC 不符，MCU 已置 FAILED、回 IDLE，旧固件继续运行。**升级失败**，如需重试从阶段一重来（通常是包顺序/尾包长度错，先自查） |
| 应答 = 1   | 下载完成，MCU 300 ms 后复位。**这不等于升级成功**，进入阶段四 |

### 阶段四：结果确认（Port `0xA2` / Cmd `0x10`）

| 项目               | 内容                                                         |
| ------------------ | ------------------------------------------------------------ |
| 先等待             | 收到 FINISHED_ACK=1（或阶段三重发耗尽）后**等 15 秒**再开始查询：BOOT 校验 + APP 启动 + 10~25 秒试运行自检 |
| SOC 发             | `5A A5 AA A2 10 [Seq] 02 01 00 [CS]`（`TLV_GET_VERSION`），例 `5A A5 AA A2 10 01 02 01 00 5F`，每 **2~3 秒**一次 |
| 应答               | `0xBB` + `TLV_REPORT_VERSION`(0x02, len=7)：`value[0..2]` = 版本 major/minor/patch，`value[5]` = 运行槽（1=A, 2=B），`value[6]` = OTA 状态 |
| 判定               | `value[5]` = 目标槽 且 `value[6]` = 4 (CONFIRMED) → **成功**；`value[6]` = 5 (FAILED) → **失败，MCU 已自动回滚旧固件**；`value[6]` = 3 (TESTING) → 自检中，继续轮询；无应答 → MCU 仍在重启/自检，继续轮询 |
| 总超时             | **90 秒**仍未得到 4 或 5 → 判失败（此时 MCU 大概率已回滚，再查一次版本确认） |
| 复位期间的串口噪声 | BOOT 会在同一串口打印 `[BOOT] ...` 文本，SOC 解析器必须按 `5A A5` 帧头同步、丢弃非帧字节，不能因为收到文本就报错 |

`v[5]/v[6]` 已经是实值，`general_comm.c` 的版本应答已经填了运行槽和 OTA 状态，不是保留 0：SOC 现在把这两个字节当保留 0 是旧协议遗留，改成按上表解析即可。抓包确认的话，升级前正常运行时应答里 `v[5]` 应为 1 或 2、`v[6]` 为 0/4/5 中的一个，不会是 0/0。

成功以谁为准 —— 以阶段四为准，`FINISHED_ACK=1` 不是成功，MCU 回 `FINISHED_ACK=1` 时只做了三件事：长度核对、整槽 CRC32、元数据写 PENDING，然后 300 ms 后复位。新固件一行都还没跑。之后 BOOT 会做 CRC 校验并进 TESTING，APP 起来后 10~25 秒自检，失败 3 次 BOOT 自动回滚旧槽——这一切 SOC 都收不到任何通知。所以 `ACK=1 就 Success` 的实现，在"新固件起不来被回滚"这种最需要报错的场景下恰恰会报成功。判定规则：`v[5] == 目标槽 && v[6] == 4` 成功；`v[6] == 5` 失败（已回滚）；`v[6] == 3` 继续等；总超时 90 秒。

## 3. 定时器汇总

| 定时器                  | 值                  | 归属    | 说明                                |
| ----------------------- | ------------------- | ------- | ----------------------------------- |
| 阶段一应答超时          | 1 s，重发 ≤ 3 次    | SOC     |                                     |
| READY 等首包            | 5 s                 | **MCU** | 阶段一应答 = 1 后 5 s 内必须发首包  |
| 首包应答超时            | 90 s，**不重发**    | SOC     | 期间静默                            |
| 数据包应答超时          | 500 ms，重发 ≤ 5 次 | SOC     | 累计必须 < 5 s                      |
| 会话空闲超时            | 5 s                 | **MCU** | 任意阶段无合法 OTA 帧 → FAILED/IDLE |
| FINISHED 应答超时       | 2 s，重发 ≤ 3 次    | SOC     | 耗尽后转阶段四，不判失败            |
| 阶段四起始等待          | 15 s                | SOC     |                                     |
| 阶段四轮询间隔 / 总超时 | 2~3 s / 90 s        | SOC     |                                     |
| 终止后重试前等待        | ≥ 6 s               | SOC     | 让 MCU 会话超时清场                 |

## 4. 参考伪代码

```python
def send_and_wait(frame, expect_tlv, expect_seq, timeout_s, max_retry):
    """发 frame，等 0xBB/Port 0xA6 或 0xA2、TLV=expect_tlv、Seq=expect_seq 的应答。
       忽略 0xBA 与 Seq 不匹配的帧。返回 1 / 0 / None(耗尽)"""
    for attempt in range(max_retry + 1):
        uart.write(frame)
        deadline = now() + timeout_s
        while now() < deadline:
            f = uart.read_frame(deadline - now())   # 内部按 5A A5 同步、校验和过滤
            if f is None:
                break
            if f.type != 0xBB or f.tlv_type != expect_tlv or f.seq != expect_seq:
                continue                            # 0xBA / 迟到 ACK / 其它上报：忽略
            if f.value[0] == 1:
                return 1
            if expect_tlv == TLV_OTA_PACKS_ACK:
                break                               # ACK=0：立刻重发同 Seq
            return 0                                # 其它阶段的 0 交给调用方判断
    return None

def ota(image_a, image_b, target_slot_first):
    # 阶段一
    r = send_and_wait(REQ_FRAME, TLV_OTA_REQ_RESULT, 0, 1.0, 3)
    if r is None: fail("MCU 无响应")
    if r == 0:    fail("MCU 拒绝 OTA（打印中/自检中），稍后重试")

    # 阶段二 A：首包，90 s，不重发；被拒就换另一槽
    for img in order_by(target_slot_first, image_a, image_b):
        r = send_and_wait(img.first_packet(seq=0), TLV_OTA_JUDGMENT_SEQ, 0, 90.0, 0)
        if r is None: fail("首包无应答，从阶段一重来")
        if r == 1:    break
    else:
        fail("两个槽的首包都被拒绝")

    # 阶段二 B：数据包，同 Seq 重发 ≤ 5 次
    for idx, chunk in enumerate(img.chunks(128), start=1):
        seq = idx & 0xFF
        r = send_and_wait(data_frame(seq, chunk), TLV_OTA_PACKS_ACK, seq, 0.5, 5)
        if r != 1:
            sleep(6); fail("数据包 %d 重发耗尽，等待 MCU 会话超时后重试" % idx)

    # 阶段三
    r = send_and_wait(FINISHED_FRAME, TLV_OTA_FINISHED_ACK, 0, 2.0, 3)
    if r == 0: fail("收尾校验失败（长度/CRC），MCU 已回 IDLE")
    # r == 1 或 None（ACK 丢失、MCU 已复位）都进入阶段四

    # 阶段四
    sleep(15)
    deadline = now() + 90
    while now() < deadline:
        v = query_version(timeout=1.0)              # 无应答返回 None
        if v and v.ota_state == 4 and v.run_slot == img.slot: return "OK"
        if v and v.ota_state == 5: return "FAILED_ROLLED_BACK"
        sleep(2.5)
    return "TIMEOUT"
```

## 5. 常见现象与处理

| 现象                                                       | 原因                                                         | SOC 处理                                                     |
| ---------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 发首包后 3~8 秒没有任何回复，连 `0xBA` 也没有              | MCU 正在擦除候选槽，CPU 停摆                                 | 正常，继续等，最多 90 s，期间不要发帧                        |
| 每包都收到两帧回复                                         | `0xBA` 通信层确认 + `0xBB` 业务应答                          | 只看 `0xBB`，`0xBA` 忽略                                     |
| 某包收到 `PACKS_ACK=0`                                     | 数据帧内容错、Seq 不是期望值、或 Flash 写失败                | 同 Seq 立刻重发；若连续多包 = 0，检查 Seq 是否从 1 开始、是否 `& 0xFF` 循环、尾包 Len 是否 4 字节对齐 |
| 重发某包后收到 `PACKS_ACK=1` 但怀疑重复写入                | 不会：MCU 对最近一包的重复 Seq 只补 ACK 不写 Flash           | 正常继续                                                     |
| 中途暂停 > 5 秒后继续，收到 `PACKS_ACK=0` 且之后一直 0     | MCU 会话已超时回 IDLE，收到的数据包全被当作错序              | 本次作废，从阶段一重来                                       |
| FINISHED 重发 3 次都没回复，随后串口出现 `[BOOT] ...` 文本 | FINISHED_ACK=1 丢了，MCU 已复位进入升级流程                  | 正常，进入阶段四轮询                                         |
| 阶段四 `value[6]` = 5                                      | 新固件试运行自检失败（3 次内未确认），BOOT 已回滚            | 升级失败，旧固件在跑；检查新固件是否兼容当前板卡配置         |
| 阶段四 `value[6]` = 1 (DOWNLOADING) 长期不变               | 上次会话中途断电，元数据停在 DOWNLOADING；MCU 复位后 BOOT 会转 FAILED | 重新发起完整 OTA 即可                                        |
| 阶段一应答 = 0                                             | 打印中或上次 OTA 自检未出结论（上电 25 秒内）                | 不是丢包，等待后重试                                         |

## 6. 不要做的事

- 不要用 `0xBA` 判断"可以发下一包"。

- 不要在首包应答等待期间发任何帧（包括心跳、版本查询）。

- 不要跳包、不要一次在途多包、不要回退两包以上重发——MCU 只去重"最近成功的一包"。

- 不要因为超时而发"新 Seq"的同一包，重发必须**原帧原 Seq**。

- 不要把 `FINISHED_ACK=1` 当作升级成功，必须走阶段四。

- 收不到应答连续重试失败后，不要立刻重新开始阶段一，先等 ≥ 6 秒让 MCU 会话超时。

  

## 7.一些信息补充

1.首包 128 字节 —— 用打包工具的文件原样发，不要自己拼 `MainBoard_OTA_Tools/bin打包合成工具/MainBoard_BIN_Packager.py` 生成的升级包就是 128 字节头 + 固件，SOC 把文件从头开始按 128 字节切片发就行，文件的前 128 字节就是首包 Value，无需拼装。

2.SOC 不需要做任何补齐。加密后的bin文件在生成升级包时已经把固件补齐了，而且补的粒度比 4 字节大得多——是补到 2048 字节的整数倍：所以 SOC 侧的规则很简单：文件大小必须等于 128 + N×128，按 128 切完直接发，一个字节都不要增删。如果 SOC 发现文件大小不是 128 的整数倍，说明拿到的不是打包工具的输出（比如误用了 Keil 直接导出的原始 .bin），应该报错而不是自己补。

3.OTA 期间串口是否禁其它命令 —— 只有擦除窗口是硬禁，其余是建议，首包发出到收到 `JUDGMENT` 之间（最长约 8 秒）：F407 单 Bank Flash 擦除时 CPU 取指停摆，任何帧都不会被处理，这是硅片级限制，与 OTA 逻辑无关。此窗口内发的命令会积压在 DMA 缓冲里等 CPU 恢复后一起处理，可能超出缓冲被丢，也不会有及时应答，所以这段不要发任何帧。其它阶段：MCU 各任务照常运行，版本查询、调试命令都会被正常处理并应答，没有互斥。但两点要注意：一是 MCU 自己的周期上报（传感器 1ST/3ST/EXT 每秒三帧、报警等 `0xBB`）在 OTA 期间不会停，SOC 的 ACK 匹配必须按 Port/Cmd/TLV/Seq 过滤，不能假设"下一帧就是我的 ACK"；二是 MCU 在打印中会拒绝 OTA 请求（`REQ_RESULT=0`），反过来 OTA 进行中 SOC 也不应下发打印、运动类命令，否则会话 5 秒超时（若被长时间阻塞）会让升级作废。最简单的做法是 OTA 期间 SOC 除 OTA 帧和阶段四的版本查询外不发别的，这是工程建议不是协议要求。
