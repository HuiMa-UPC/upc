4. 每个文件里什么行有用
4.1 topic_boot_lifecycle.log
每次进程拉起写一行：
PROCESS_BOOT proc=<名字> pid=<pid> boot_id=<内核启动号> uptime_s=<秒> prev_clean=<0或1> prev_pid=<上次pid> prev_ts=<上次unix秒>
字段
有用的读法
boot_id
同一次上电的所有进程这个值相同。变了就是整机重启过
uptime_s
内核已运行秒数。很小说明刚上电；很大但进程 pid 变了，说明只是这个进程被拉起
prev_clean=1
上次进程自己正常退出
prev_clean=0
上次没走到正常退出，常见于崩溃、掉电、被杀死
prev_clean=-1
没有上次记录，多半是第一次启动或状态文件丢了
七个进程各自有一行。缺某个进程的 PROCESS_BOOT，就是那个进程没起来。两次 PROCESS_BOOT 之间的裸文本（没有 level=）是崩溃输出或库报错。

4.2 topic_system_resource.log
约每 5 秒一行，module=HostMonitor：
cpu_sys=12.5% cpu_proc=3.0% temp=62.0C z4=58.0C mem_avail=800MB/1024MB rss=120MB
读不到温度时 temp=N/A、z4=N/A，这一行的级别是 WARN。
字段
含义
cpu_sys
整机 CPU 占用
cpu_proc
写这条日志的那个进程自己的占用。看行里的 proc=
temp
CPU 温度，摄氏
z4
thermal_zone4 温度，摄氏
mem_avail/mem_total
可用内存 / 总内存，MB
rss
该进程驻留内存，MB
cpu_sys 长时间接近 100，或 mem_avail 持续下降到很小，再去对同一时间的预览、打印日志。

4.3 topic_misc.log
正常运行这里应该几乎没有业务行。出现成片 module= 时，说明有日志没归进专题文件。把整行时间、proc、module 和正文交给研发，不要把它当成某一类传感器或打印日志。

4.5 topic_ipc_message.log 与 topic_msgbus_local.log
默认不记录每一条消息。只有 IPC_DELIVER miss 这类 WARN 会在投递失败时出现，表示没有订阅者收到这条消息。
打开逐条跟踪后，正文是 IPC_TX、IPC_RX、IPC_DELIVER，以及进程内的发布和入队。这种包很大，只在研发要求时打开。

4.9 topic_tcp_motion_tx.log 与 topic_tcp_heartbeat.log
急停、暂停、红光这些紧急指令默认会记：
tcp emergency sent stop=<值>
tcp emergency send failed rc=<值>
sent 是已经交给振镜链路。send failed 是没发出去。
TCP_TX frame[ 是每一帧运动数据的十六进制，默认关闭，打开后文件会很大。只在要核对某一帧内容时打开 UPC_GLAVO_LOG_TCP_TX=1。
心跳文件默认也几乎是空的。打开 UPC_GLAVO_LOG_TCP_HEARTBEAT_RSP=1 且级别为 debug 后才有：
tcp hb rsp cmd_rate=<指令速率> data_rate=<数据速率> event=0x<事件> ota=<0或1>
ota=1 表示当时振镜侧认为正在升级。长时间没有心跳且运动发不出去，先看本文件有没有 finish wait: drain still pending，再看 topic_print_flow.log 里 TCP 是否断开。

4.10 topic_laser_power.log
功率变化时才写一行，相同功率不重复刷：
laser_power_set raw=<整数>

raw 是实际下发值。界面功率变了这里却没有新行，说明没发到振镜链路。这里没有界面设定值和实测值的对比句，对比要自己把界面记录和这行对齐。

关键字

4.15 topic_ui_preview.log
预览问题先在这个文件里搜 decode ready，这行是 INFO，默认看得到：
decode ready scene=<场景> image=<指针> <宽>x<高>@<帧率> fps out=<输出宽>x<输出高> crop=<起始行>+<行数> scaled=<0或1> frame_bytes=<字节> rga_path=<0或1> ...
字段
含义
scene
谁在看。监控页预览和别的场景名字不同
宽x高@帧率
相机送来的尺寸和帧率
out
实际画到屏幕上的尺寸
scaled
1 用硬件缩放。0 退回不缩放，屏幕再自己缩放，会更吃 CPU
rga_path
1 硬件转换。0 软件转换，每帧更慢
硬件失败时会有 RGA dma32 alloc failed、RGA streaming cache、falling back to software。画面还能有，只是更卡。stream start give up、dma frame ring open failed、dma fd count mismatch 则是预览没建立起来。
默认不写、把级别调到 debug 之后才有的 5 秒统计：
stream 5s: committed=<帧> last_seq=<序号> last_slot=<槽> slot_fail=<次> dequeue_fail=<次> release_timeout=<次> inflight_max=<在飞>/<上限> drv_age_avg_us=<微秒> drv_age_max_us=<微秒> drv_drop=<丢帧> drv_drained=<排空> ts_mono=<0或1>
这行的 proc 是 rongsu_camera。30 帧每秒时，5 秒 committed 大约 150。slot_fail、dequeue_fail、release_timeout、drv_drop 持续大于 0，就是采集或消费者跟不上。
decode 5s: scene=<场景> ok=<帧> fail=<帧> skip=<帧> no_frame=<帧> ... cvt_avg_us=<微秒> cvt_max_us=<微秒> rga=<0或1> shm_wait_avg_us=<微秒> show_avg_us=<微秒> show_n=<帧>
这行的 proc 是 rongsu_ui。ok 应接近上面的 committed。fail 持续大于 0 是转换失败。no_frame 很大是界面没拿到新帧。rga=1 且 cvt_avg_us 大约几千微秒是硬件路径；软件路径会到两万微秒量级。skip 是手指滑动时故意少做转换，取帧仍在继续。
uiloop 5s: loops=<圈数> ipcwait_avg_us=... lv_avg_us=... ipc_avg_us=... mon_avg_us=...
refr 5s: n=<次> idle=<次> refr_avg_us=... pre_avg_us=... draw_avg_us=... wait_avg_us=... waits=<次> flush_avg_us=... flushes=<次>
loops 是 5 秒内界面主循环圈数，明显变少就是界面线程被拖住。refr 是一次刷屏：pre 布局和缓冲拷贝，draw 绘制，wait 等屏幕翻页，flush 提交。draw 很大时优先怀疑预览被软件缩放（decode ready 里 scaled=0）。

4.24 topic_mqtt_wire.log
云端收发的原文，全部是 DEBUG，默认文件为空。打开 UPC_LOG_MIN_LEVEL=debug 之后：
MQTT TX frame topic=<主题> qos=<0或1> retained=<0或1> len=<字节>
MQTT TX payload topic=<主题> chunk=<第几段> range[<起>..<止>/<总长>]="<正文>"
RX 是云端下来的。一条 JSON 可能拆成多个 chunk，按 range 的起点拼接。正文里的引号和换行已经转义。主题里能看出种类：heartbeat、telemetry、ota/check、ota/check_ack、ota/progress、alarm/report、state。

5. 把一次故障串起来
1. 在 topic_boot_lifecycle.log 用现象发生时的 boot_id 确认没有夹进另一次重启。
2. 用第 2 节打开一个主文件，记下 ERROR 或关键行的时间，精确到秒即可。
3. 用同一秒去第二个文件里搜。进程不同没有关系，时间是对齐的。
4. 环境数值以 soc: / sensor: 为准，界面只是它的显示。valid 对应位为 0 或数值为 -1.0 时，界面显示 -- 是对的。
5. 默认包里没有 DEBUG 行。结论不要写成「日志里没有心跳原文所以没上报」，先看有没有 publish heartbeat fail 这种 WARN。
可选脚本 tools/analyze_topic_logs.py 能把一部分行收成 CSV 和网页。脚本里的正则如果和本手册的行对不上，以本手册为准，以当前日志原文为准。
