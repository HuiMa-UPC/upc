## 〇、设备端要做的事（TL;DR）

一次打印任务，设备端从装载 3mf 到完成，共四条上行 / 一条下行 / 一次 HTTP 直传：

| 阶段 | 动作 | 通道 | 载具 |
|------|------|------|------|
| 1 申请作业号 | 上行 `print_job/request`，带自己生成的 `req_id` | MQTT QoS1 | §5.1 |
| 2 收作业号 | 下行 `print_job/ack`，带云端生成的 `job_id` + 缩略图预签名 | MQTT QoS1 | §5.1 |
| 3 上报事实 | 上行 `print_task/report`，带 `job_id` + 模型名 + plate_meta | MQTT QoS1 | §5.2 |
| 4 传缩略图 | HTTPS PUT 到 `uploadUrl`，body = 缩略图字节 | 对象存储直传 | §5.3 |
| 5 回执 | 上行 `print_thumbnail/ack`，回显 `objectKey` | MQTT QoS1 | §5.3 |
| 6 状态贯穿 | 打印过程心跳里带同一 `job_id`（复用既有心跳协议） | 既有心跳 | §八 |

## 一、身份键与字节规范（红线，先读）

两个 32 位小写 hex 键，格式相同、生成方不同、各管一段。字节级一致是硬门槛，任何一处漂移都会断开链路。

| 键 | 生成方 | 格式 | 语义 |
|----|--------|------|------|
| `req_id` | **设备端** | UUID v4，32 位小写 hex，去连字符 | 申请幂等键：一次装载动作一个，超时重试复用，新装载新建 |
| `job_id` | **云端** | UUID v4，32 位小写 hex，去连字符 | 任务业务主键：申请时下发，后续所有上报贯穿 |

**字节规范（两条共用）：**

- 格式：UUID v4（版本位 = 4、变体位 = 8/9/a/b）
- 大小写：全小写 hex
- 连字符：去掉，32 字符
- 生命周期：一次生成后全生命周期字节不变，禁止每次上报重新 `toString()`
- `job_id` 只有云端能生成，设备端自生成的 job_id 不入流

**设备端必须保证的字节链：**

- 申请时自己生成的 `req_id`，在超时重发时原样复用，一个字符都不能变
- 下行拿到的 `job_id`，在 `print_task/report`、`print_thumbnail/ack`、心跳里逐字节一致
- 回执的 `objectKey` 必须逐字节等于下行 ack 里的 `objectKey`（见 §5.3，否则回执被判失败不落库）

## 二、消息封套（通用顶层）

所有打印任务消息共用一个封套，顶层固定字段如下：

| 字段 | 类型 | 闭集 / 约束 | 条件存在 | 语义 |
|------|------|-------------|---------|------|
| `v` | int | `1` | 必备 | schema 版本，新增字段递增，接收端忽略未知字段 |
| `type` | string | 见各消息枚举 | 必备 | 消息类型（云端当前不校验，见 §三） |
| `device_id` | string | 设备序列号（遵循主协议 device_id 定义） | 必备 | 设备唯一 ID |
| `ts` | int64 | ≥0，UTC 毫秒 | 必备 | 消息产生时刻，NTP 对时后可信 |
| `seq` | uint32 | 单调递增，重启可归零 | 必备 | 配合 `ts` 做去重 / 丢包检测 |
| `req_id` | string | 32 位小写 hex 去连字符 | 仅 request / ack 出现 | 申请幂等键、请求应答关联 |
| `data` | object | 结构由 `type` 决定 | 必备（可为 `{}`） | 业务体 |

**分层原则（硬条款，按表抄，别记笼统口号）：**

```text
req_id  → 封套顶层（申请幂等键，申请完成后使命结束）
job_id  → data 层（任务业务主键，贯穿全程）
业务体   → data 层
```

| 字段 | 层 | request | ack | report | thumbnail_ack |
|------|----|---------|-----|--------|---------------|
| `req_id` | 顶层 | 必备 | 必备 | 不出现 | 不出现 |
| `job_id` | data | 不出现 | 必备 | 必备 | 必备 |

## 三、云端校验 vs 单向约束（哪些有兜底、哪些没有）

下面把本文每一处「写死」标注云端到底校不校验。**硬校验**是云端会拒或会对账、写错有兜底可见；**软读（静默）**是云端只 get 不校验、写错静默进默认分支或缺键丢弃；**软读（带后果）**是按值查行、字节漂移不拒但落错行。固件不要认为「文档写死了，云端一定帮着校验」——软读的每一处，写错都只能靠固件自己守。

| 契约 | 云端校验 | 写错后果 |
|------|---------|---------|
| `objectKey` 逐字节 = 权威 key（`thumbnail/{sn}/{job_id}`） | **硬校验** | 不等 → 判对账失败不落库，留 WARN + Counter 可见 |
| `req_id` 申请去重（复用返回同 `job_id`） | **硬校验** | 按 request_id 查重 + UNIQUE 兜底并发；复用返回同 job_id |
| `job_id` 字节贯穿（跨消息一致） | 软读（带后果） | 按值查行 upsert，字节漂移不拒，但落到不同行、任务事实分裂 |
| `type` 枚举值（`print_job_request` 等） | 软读（静默） | consumer 不读 type、按 topic 路由，写错静默 |
| `req_id` 位置（封套顶层） | 软读（静默） | 按 key 精确读，放错层 → 取不到 → 判缺键丢弃 |
| `req_id` 格式（32 位小写 hex） | 软读（静默） | 只判非空，格式不符仍入流 |
| `job_id` 位置（data 层） | 软读（静默） | 放错层 / 写错 key → 取不到 → 判缺键丢弃 |
| `job_id` 格式（32 位小写 hex） | 软读（静默） | 只判非空，格式不符仍入流 |
| `objectKey` 字段名字母（K 大写） | 软读（静默） | 写错 key → null → 判缺键丢弃 |
| `model_name` / `plate_meta` 类型 | 软读（静默） | instanceof 稳健读，类型漂移落 null 不炸 |
| `plate_meta.material` / `print_time_s` | 软读（静默） | 类型漂移落 null；权威是 raw JSONB，由前端 fail-closed 兜底 |

**谱系同根（不属本文档、下波统一议）：** 上述「软读」与 register 入口不强制统一大写是同一类问题——约定写在了文档、没落成代码校验。本文档先把「写死」和「云端兜底」诚实切开，校验缺失的治本统一排下波，不在本轮改代码。

## 五、消息定义

### 5.1 申请 job_id（`print_job/request` → `print_job/ack`）

**上行 `print_job/request`（设备端 → 云端）：**

```json
{
  "v": 1,
  "type": "print_job_request",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1756960000000,
  "seq": 41,
  "req_id": "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "data": {}
}
```

| 字段 | 类型 | 约束 | 语义 | 云端校验 |
|------|------|------|------|---------|
| `type` | string | `print_job_request` | 申请类型标识 | 不校验 |
| `req_id` | string | 32 位小写 hex，封套顶层 | 申请幂等键，设备端生成 | 只判非空 + 去重 |
| `data` | object | `{}` | 无业务体（云端才生成 job_id） | — |

**下行 `print_job/ack`（云端 → 设备端）：**

```json
{
  "v": 1,
  "type": "print_job_ack",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1756960000120,
  "seq": 9,
  "req_id": "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "data": {
    "job_id": "f6e5d4c3b2a1f6e5d4c3b2a1f6e5d4c3",
    "uploadUrl": "https://...X-Amz-Signature=...",
    "objectKey": "thumbnail/SNOWPOD-A1B2C3D4/f6e5d4c3b2a1f6e5d4c3b2a1f6e5d4c3",
    "uploadUrlExpiresAt": 1756961800
  }
}
```

| 字段 | 类型 | 约束 | 语义 |
|------|------|------|------|
| `type` | string | `print_job_ack` | 申请响应标识 |
| `req_id` | string | 原样带回（字节不变） | 关联 `print_job/request` |
| `data.job_id` | string | 32 位小写 hex，data 层 | 任务业务主键，后续全链路贯穿 |
| `data.uploadUrl` | string | 预签名 PUT URL，时效内有效 | 缩略图直传地址 |
| `data.objectKey` | string | `thumbnail/{sn}/{job_id}` | 对象 key，固定命名覆盖写幂等 |
| `data.uploadUrlExpiresAt` | number | epoch 秒，≥当前时刻 | 预签名失效时刻 |

**`data` 字段命名大小写警示（逐字照抄，别按习惯改名）：**

`data` 层这四条里命名分两套：`job_id` 走打印协议下划线，`uploadUrl` / `objectKey` / `uploadUrlExpiresAt` 走日志采集线驼峰。JSON 字段名大小写敏感，照上表字面抄：

- `uploadUrl`（U 大写）
- `objectKey`（K 大写）
- `uploadUrlExpiresAt`（U、E 大写）

别按"打印协议其余字段都下划线"的老习惯写成 `upload_url` / `object_key` / `upload_url_expires_at`。抄错一个字，回执对账取不到 `objectKey`，缩略图链路无声断（此条属 §三 软读静默，云端不会提醒你写错）。

### 5.2 任务事实上报（`print_task/report`）

**上行 `print_task/report`（设备端 → 云端）：**

```json
{
  "v": 1,
  "type": "print_task_report",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1756960000000,
  "seq": 42,
  "data": {
    "job_id": "f6e5d4c3b2a1f6e5d4c3b2a1f6e5d4c3",
    "model_name": "bracket_v3",
    "plate_meta": {
      "layer_height_mm": 0.03,
      "layers": 796,
      "material": "Material-02",
      "parts": 53,
      "plate_id": 0,
      "print_time_s": 0,
      "reserved1": null,
      "reserved2": null,
      "schema": "snowpath_plate_meta_v1"
    }
  }
}
```

| 字段 | 类型 | 约束 | 语义 |
|------|------|------|------|
| `type` | string | `print_task_report` | 上报类型标识 |
| `data.job_id` | string | 32 位小写 hex，data 层 | 与申请章 job_id 逐字节一致 |
| `data.model_name` | string | 3mf 文件名（设备原样），长度 ≤256 | 模型名 = 3mf 文件名 |
| `data.plate_meta` | object | schema `snowpath_plate_meta_v1` 整包透传 | 3mf 内嵌 plate_meta，字段演进不翻表 |

**plate_meta 字段表（schema `snowpath_plate_meta_v1`）：**

| 字段 | 类型 | 约束 | 语义 |
|------|------|------|------|
| `layer_height_mm` | number(float) | ≥0 | 层高（毫米） |
| `layers` | int | ≥0 | 总层数 |
| `material` | string | 材料号，长度 ≤128 | 预计耗材口径（撤克数值，3mf 无克数） |
| `parts` | int | ≥0 | 部件数 |
| `plate_id` | int | ≥0 | 平台号 |
| `print_time_s` | int | ≥0；`0` / 缺失 = 未知 | 预计耗时（秒） |
| `reserved1` | any | `null` | 预留 |
| `reserved2` | any | `null` | 预留 |
| `schema` | string | `snowpath_plate_meta_v1`（常量） | plate_meta 版本号 |

**空态语义：**

| 空态项 | 语义 |
|--------|------|
| `print_time_s` = 0 或缺失 | 云端 / 前端显示为空态，不显示 `0s` |
| `model_name` 缺失 | 前端甘特图标签不挂 |
| 缩略图未回执 | 前端占位图 |

### 5.3 缩略图直传与回执（`print_thumbnail/ack`）

缩略图（二进制）不进 MQTT/Kafka，走对象存储直传。分三步：

**① 预签名申请**：已并入 `print_job/ack`（§5.1），无需单独上行。`uploadUrl` / `objectKey` / `uploadUrlExpiresAt` 随 job_id 一起下发。

**② HTTP 直传（设备端 → 对象存储）：**

- 方法：HTTPS PUT
- body：缩略图字节
- 目标：`uploadUrl`
- 时效：`uploadUrlExpiresAt` 内传完

**③ 回执（设备端 → 云端）：**

```json
{
  "v": 1,
  "type": "print_thumbnail_ack",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1756960015000,
  "seq": 43,
  "data": {
    "job_id": "f6e5d4c3b2a1f6e5d4c3b2a1f6e5d4c3",
    "objectKey": "thumbnail/SNOWPOD-A1B2C3D4/f6e5d4c3b2a1f6e5d4c3b2a1f6e5d4c3"
  }
}
```

| 字段 | 类型 | 约束 | 语义 | 云端校验 |
|------|------|------|------|---------|
| `type` | string | `print_thumbnail_ack` | 回执类型标识 | 不校验 |
| `data.job_id` | string | 32 位小写 hex，data 层 | 命中 `print_task` 行 | 只判非空 + 按值查行 |
| `data.objectKey` | string | 与下行 ack 的 `objectKey` 一致 | 回执对象 key，云端回显对账 | **硬校验（逐字节比对）** |

**`objectKey` 规范（回显对账，逐字节，硬校验）：**

- 命名：`thumbnail/{device_id}/{job_id}`，下行 ack 已下发，设备端回执原样回显
- 回执 `objectKey` 必须逐字节等于下行下发的 `objectKey`，否则云端判对账失败、不落库（WARN + Counter 可见）
- 覆盖写天然幂等，重试不产生孤儿对象
- `objectKey` 里的 `device_id` / `job_id` 与封套 / data 层对应字段逐字节一致

## 六、端到端时序

```
desktop                        设备端（固件）                        云端
   │                              │                                  │
   │  ① 3mf 文件                    │                                  │
   │  （模型/缩略图/plate_meta）      │                                  │
   │─────────────────────────────>│                                  │
   │                              │  ② print_job/request (req_id)     │
   │                              │─────────────────────────────────>│
   │                              │                                  │ 生成 job_id + insert 占位行
   │                              │  ③ print_job/ack                  │
   │                              │  (job_id + uploadUrl/objectKey/   │
   │                              │   uploadUrlExpiresAt)             │
   │                              │<─────────────────────────────────│
   │                              │                                  │
   │                              │  ④ HTTPS PUT 缩略图 → 对象存储      │
   │                              │  (body=缩略图字节, 时效内传完)        │
   │                              │                                  │
   │                              │  ⑤ print_task/report              │
   │                              │  (job_id + model_name + plate_meta)│
   │                              │─────────────────────────────────>│ 更新四样事实
   │                              │                                  │
   │                              │  ⑥ print_thumbnail/ack            │
   │                              │  (job_id + objectKey 回显对账)      │
   │                              │─────────────────────────────────>│ 回补缩略图 key
   │                              │                                  │
   │  打印执行中…                  │  ⑦ 心跳带 job_id（§八）            │
   │                              │─────────────────────────────────>│ 投影状态机
```

④⑤⑥ 三条腿顺序可乱：云端按 `job_id` 幂等落同一行，先到先落、后到补齐。缩略图直传不依赖打印完成，装载时即可传；`print_task/report` 建议在装载完成后尽早发，保证事实行尽早完整。

## 七、错误处理与重试（幂等语义）

**申请幂等（`req_id`）：**

- 一次「装载 3mf 并发起打印」= 一个 `req_id`
- 超时未收到 `print_job/ack`，**复用同一 `req_id` 重发**，云端去重返回已绑定的同一 `job_id`
- 新装载（哪怕同一个 3mf 文件）**必须生成新 `req_id`**，否则云端会当重试返回旧 `job_id`，把二次打印误认成首次

**预签名重签（复用 `req_id` = 重签）：**

- `uploadUrl` 过期：复用同一 `req_id` 重发 `print_job/request`，云端重新签名下发三字段
- 重签不换 `job_id`、不新增任务行，仅刷新 `uploadUrl` / `uploadUrlExpiresAt`
- `objectKey` 固定命名，重签前后字节不变，覆盖写幂等

**回显对账（硬校验）：**

- 回执 `objectKey` 与下行 `objectKey` 逐字节比对，相等才落库；不等判对账失败不落库
- 设备端只需保证：回执里的 `objectKey` 原样复制下行 ack 里的 `objectKey`，不改动、不重建

**离线边界（已定）：**

- 离线申请不在本期范围，不设计「阻塞开打 / 事后补登」降级
- 设备装载 3mf 时须在线完成申请，申请未成功不得开打

## 八、状态上报（`job_id` 贯穿，复用既有心跳）

打印任务的状态机继承既有心跳协议，设备端**不新增**状态上报 topic。要领只有一条：**打印过程中，心跳里带的 `job_id` 与申请到的 `job_id` 逐字节一致。**

云端据此把 `print_task.status` 投影为四态：

| status | 设备端驱动源（心跳 job.mode） |
|--------|------------------------------|
| `REQUESTED` | 申请 job_id 时占位（四样全空，甘特图不展示） |
| `RUNNING` | `purge` / `printing` / `unload` |
| `COMPLETED` | `complete` |
| `CANCELLED` | `cancel` |

设备端只需继续按既有心跳协议上报 `state_history.job`（含 `job_id` 与 `mode`），云端自动归并时间轴、投影状态。核心约束仍是一条：`job_id` 字节级一致（见 §三 软读带后果：漂移不拒，但时间轴与任务事实的 join 会静默断开）。
