## 一、结论速览

| 维度 | 冻结口径 |
|---|---|
| 密钥派生 | HKDF-SHA256（RFC 5869），IKM = activation_secret_hash 的 hex 串 UTF-8 字节，salt = 下发 base64 解码后的二进制 |
| 加密 | 先打包 tar.gz → 整体 AES-256-GCM 加密一次（单文件也打成 tar） |

## 二、密钥派生（HKDF-SHA256）

### 2.1 IKM

- **IKM = activation_secret_hash 的 hex 串 UTF-8 字节**，即 `sha256Hex(device_secret)` 得到的 64 字符十六进制字符串，按 UTF-8 编码的字节（64 字节 ASCII）。
- **不是** `sha256(device_secret)` 的 raw 32 字节，也**不是** device_secret 的明文原始字节。
- 选它作 IKM 的原因（2026-09-05 拍板 B）：云端 Device 表只存 `activation_secret_hash = sha256(device_secret)`，明文 device_secret 注册时即丢弃、单向不可反推。云端能拿到且设备端能同源算出（`sha256Hex(deviceSecret)`）的唯一共同材料就是这串 hex，于是把它定为 IKM 原材料，从「半敏感摘要」升级为「解密能力的地基」——泄露它即泄露解密能力，故在 Device 实体上 `@JsonIgnore` + `@ToString.Exclude` 钉死不可序列化。
- 字节级铁律：喂 HKDF 的是 **64 字符 ASCII 的 UTF-8 字节**（如 `abc...` 逐字符 ASCII），**不是**先 hex-decode 成 32 字节。两端必须同源同编码，差在这一拍密钥即对不上。
- 设备端同源实现：`sha256Hex(device_secret)`（先对原始 secret 做 SHA-256，得 32 字节，再 hex 编码成 64 字符字符串），取该 hex 字符串的 UTF-8 字节作 IKM。字符串必须**小写 hex**——云侧 SecurityUtils.sha256Hex 已钉 `%02x` 小写，设备端 hex 编码若出大写（A-F）即与云侧分叉、密钥对不上。

> 对照：激活链路（`device_activation.cpp`）是 `SHA256(device_secret.data(), device_secret.size())` 得 32 字节 HMAC key（raw 字节）。日志采集 HKDF 用**同一 sha256 结果的 hex 串**（UTF-8），但用途经由 info 域分离与激活签名隔离。

### 2.2 salt

- 来源：下行指令 `data.encrypt.salt`（base64 字符串，16 字节随机，每次采集独立）。
- HKDF 的 salt = **base64 解码后的二进制**，不是 base64 字符串本身。
- 设备端在回执里回显的是**下行原文 base64**，不要解码后再编一次（padding 可能对不齐）。

### 2.3 info 与输出

- HKDF-SHA256，信息提取 + 扩展：
  - `PRK = HKDF-Extract(salt, IKM)`，hash = SHA-256
  - `KEY = HKDF-Expand(PRK, info, 32)`，输出 **32 字节**
- `info` = `snowx:iot:log-collect:enc:v1`（域分离标签，逐字节固定，双方一致）

## 三、打包与加密流程

1. 按 `topicFiles` 顺序收集日志明文。
2. **永远打成 tar.gz**（单文件也打成 tar，内含 1 项）。objectKey 后缀恒定 `.tar.gz`，不再按清单条目数猜（`topicFiles.size()` 是清单条目数、非设备物理文件数）。
3. 对 tar.gz 明文**整体 AES-256-GCM 加密一次**：
   - key = 第二节派生的 32 字节密钥
   - nonce = 12 字节随机，每次加密独立生成（**绝不复用**）
   - AAD = `v1:` + collectId
4. 密文布局：`nonce(12) ‖ ciphertext ‖ tag(16)`。nonce 前置、tag 后置，与 ciphertext 构成**同一条字节流**，整个一起 PUT 进对象（不放 x-oss-meta 元数据）。

### 3.1 nonce 红线

- **同一 key 下 nonce 绝不重复**。这是 GCM 唯一的硬红线，nonce 复用会导致认证密钥流重用，密文可被解可被伪造。
- 每次加密重新生成 nonce；设备重启 / 重传也不复用旧 nonce；不缓存 nonce。
- 选用 12 字节是因为 GCM 标准 nonce 长度即 96 bit，其他长度会引入额外运算且易错。

## 四、字节基准

设明文 tar.gz 长度为 L，则：

- **ciphertext 长度 = L**（AES-GCM 是流模式，不填充，密文长度 = 明文长度）。
- **上传对象总长 = L + 28 = nonce(12) + ciphertext(L) + tag(16)**。
- **fileSize = 12 + n + 16**，n 为 ciphertext 长度，与对象实际字节数（headObject 的 size）严格一致。

| 字段 | 口径 |
|---|---|
| `fileSize` | 上传对象实际总字节，平台 headObject 比对、不符判失败；双口径：加密态 = 12 + n + 16，明文态 = 明文 tar.gz 实际大小 |
| `maxPacketSize` | **上传对象（PUT body）上限**，与加密开关脱耦、与 fileSize 同口径。加密态：`L + 28 ≤ maxPacketSize`，明文包上限 = `maxPacketSize − 28`；明文态：`L ≤ maxPacketSize`，不预留 28 |
| `fileReport[].size` | 各文件**明文**贡献字节数，只展示、平台不对此对账 |

> 设备端打包时按「加密态明文 tar ≤ maxPacketSize − 28，明文态明文 tar ≤ maxPacketSize」判超限：加密态预留 nonce+tag 的 28 字节开销，明文态无加密开销、不预留。超限则整文件撤出（标 `size_exceeded`）重打 tar。仅当打包实现异常、上传对象（PUT body）仍超 maxPacketSize 时，才回任务级 `SIZE_EXCEEDED` 兜底。

> **fileSize 双口径（部署开关分流，设备端必读）**：
> - **明文态**（`log-collect.encrypt-enabled=false`）：不上加密，`fileSize` = 上传的明文 tar.gz 实际字节数，不套 `12 + n + 16`。
> - **加密态**（`encrypt-enabled=true`）：`fileSize` = `12 + n + 16` = 明文 tar.gz 大小 + 28。
> - 平台比对是 `meta.getSize() != fileSize` 的 **long 精确等值判死**（不是范围）。设备回传 `fileSize` 必须等于本任务实际上传对象的字节数；明文/密文两口径混用（把明文 tar 大小报成密文、或反之）会差 28 字节，当场判 `LOG_CONTENT_MISMATCH`。

## 五、云端解密流程（对称实现，校验侧落地依据）

1. 从 `task.encryptParams` 取 salt（base64）→ 解码成二进制。
2. IKM = 该设备 `activation_secret_hash` 的 hex 串 UTF-8 字节（即存库的 `sha256Hex(device_secret)` 字符串本身，64 字符 ASCII）。
3. `KEY = HKDF-SHA256(salt_binary, IKM, info=snowx:iot:log-collect:enc:v1, L=32)`。
4. 取对象字节流前 12 字节 = nonce，末 16 字节 = tag，中间 = ciphertext。
5. `AAD = "v1:" + collectId`。
6. AES-256-GCM 解密 + 验 tag（tag/AAD 不符即判篡改或替换）。
7. 解 tar.gz 得明文日志。

解密管线已落地：04178b4（HkdfUtils + LogCollectCrypto + 独立 KAT 向量）、5e6dded（onCollectAck 接入验 tag）、d35764e（错误码按族分流）。历史任务 salt 缺失 WARN 跳过、不判失败；解密三刀（salt 非法 base64 / activationSecretHash 缺失 / AEAD 认证失败）→ `LOG_DECRYPT_FAILED`(422)，读对象失败 → `LOG_CONTENT_MISMATCH`（未进解密、与 headObject 失败同族），均不静默降级。

## 六、失败原因闭集

### 6.1 任务级 `result=error` 的 `reason`（七值，设备端只填这些）

| reason | 含义 |
|---|---|
| `URL_EXPIRED` | 上传 URL 已过期 |
| `PUT_FAILED` | 预签名 PUT 失败（签名/网络/403 等） |
| `DISK_FULL` | 打包中间产物写盘失败（磁盘满） |
| `ENCRYPT_FAIL` | 加密过程出错 |
| `NO_FILE_FOUND` | 清单文件全未收集到（全空），不 PUT |
| `SIZE_EXCEEDED` | 上传对象（PUT body）仍超 maxPacketSize（兜底，正常靠压包时判超限避免） |
| `INTERNAL` | 其他内部错误 |

> 指令格式错、device_id 不符等，走既有 `rejected + invalid_state`，**不塞进这七值**。

### 6.2 逐文件 `fileReport[].reason`（四值，与任务级不混用）

| reason | 含义 |
|---|---|
| `not_found` | 采集窗内该文件不存在 |
| `empty` | 文件存在但内容为空 |
| `size_exceeded` | 纳入后超 maxPacketSize，整文件跳过 |
| `unknown` | 平台兜底补，设备端不填 |

## 七、工程红线

1. **全空语义**：清单文件全 not_found → `result=error, reason=NO_FILE_FOUND`，**不 PUT**；`detail` 至少带 collectId。
2. **fileReport 走 MQTT 回执明文**，不回进 tar（进了 tar 被加密，云端解完才读得到，且全空场景无文件可打包会卡死）。
3. **nonce 与 tag 进对象字节流**，不放 x-oss-meta 元数据，否则 headObject size 对不上。
4. **CRLF 坑**：key 文件用 getline 读取会残留 `\r`，激活和 HKDF 会一起把 `\r` 吃进 IKM。烧录保持 LF，与云端存储去空白一致。
5. **AAD / info 逐字节一致**：`v1:` + collectId 与 info 字符串，差一个冒号/空格/大小写即 GCM 认证失败、解不开。
