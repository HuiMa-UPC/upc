# 设备端日志采集对接手册

> 版本：v1.1（2026-09-04，设备侧实现口径对齐）
> 定位：面向设备端（SoC / 固件团队）的日志采集对接规范，说明设备端要实现的 MQTT 行为与消息格式
> 依据：《设备通信协议-数据结构定义（v0.9）》§二 / §七；后端实现 `iot-command-downlink` 的 `LogCollectTaskServiceImpl`（指令下发与校验）、`CmdAckConsumer`（应答处理）、`EmqxPublisher`（消息封套）
> 状态边界：日志采集主线已闭环可联调；「设备日志权威清单同步（阶段B）」未开放，见 §九
> 设备实现：`app/mqtt/lib/mqtt_service_log_collect.cpp`（`rongsu_mqtt`）

## 一、对接前置

| 项 | 要求 |
|---|---|
| 传输 | MQTT（设备当前实现为 3.1.1 + QoS 1；平台侧 MQTT 5.0 兼容） |
| Broker | EMQX；TLS 8883，明文 1883 仅限本地联调 |
| 认证 | 设备 SN 作为用户名 + MQTT 密码（激活时云端下发） |
| 身份 | 云端以 MQTT 认证身份（device_sn）为准，payload 里的字段仅作校验 |

**Topic 前缀**：`snowpod/{region}/{device_id}/`，`{region}` = `cn`（国内）/ `intl`（国际），`{device_id}` = 激活时分配的设备 SN。

**通信面划分**：

- **信令走 MQTT**：采集指令与应答全部走 MQTT（`cmd` / `cmd/ack`）
- **日志文件走 HTTPS**：日志本体直传对象存储预签名 URL（自带签名 + 时限），设备端**不做任何 URL 拼接**

## 二、消息封套（所有消息共用）

```json
{
  "v": 1,
  "type": "command",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "req_id": "7f3a1b2c4d5e6f7a8b9c0d1e2f3a4b5c",
  "data": {}
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `v` | int | 是 | schema 版本，当前 `1` |
| `type` | string | 是 | 消息类型：下行 `command`，上行 `command_ack` |
| `device_id` | string | 是 | 设备唯一 ID（= SN） |
| `ts` | int64 | 是 | Unix 毫秒时间戳 |
| `seq` | uint32 | 是 | 单调递增序号，配合 ts 做去重与乱序判定 |
| `req_id` | string | 是 | 请求-应答关联键；指令下发生成，设备应答时**原样带回** |
| `data` | object | 是 | 业务体 |

## 三、整体流程

```
Web 端建任务
   │  ① 下发 MQTT 指令 cmd=log_collect（snowpod/{region}/{sn}/cmd）
   ▼
设备端收到指令
   │  ② 按 topicFiles 收集 /var/log/topic 下当前文件 + logrotate 归档
   │     （F / F.N / F.N.gz，有什么收什么；忽略 timeRange*）
   │  ③ 一律打包 .tar.gz → AES-256-GCM 整包加密 → HTTPS PUT 预签名 URL
   ▼
设备端发应答 cmd_ack（snowpod/{region}/{sn}/cmd/ack）
   │  ④ result=accepted + detail（collectId/objectKey/fileSize/fileReport/...）
   │     或 result=rejected/error（失败原因）
   ▼
平台校验（对象大小比对 + 逐文件对账）
```

设备端只需做三步：**收指令 → 采集上传 → 回执**。状态推进由平台完成。

## 四、下行指令 `log_collect`

Topic：`snowpod/{region}/{device_id}/cmd`，QoS 1，`type=command`

```json
{
  "v": 1,
  "type": "command",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "req_id": "7f3a1b2c4d5e6f7a8b9c0d1e2f3a4b5c",
  "data": {
    "cmd": "log_collect",
    "collectId": "0f3a1b2c4d5e6f7a8b9c0d1e2f3a4b5c",
    "objectKey": "logs/SNOWPOD-A1B2C3D4/0f3a1b2c....tar.gz",
    "topicFiles": ["topic_mqtt_wire.log", "topic_print_flow.log"],
    "maxPacketSize": 10485760,
    "uploadUrl": "https://oss.example.com/bucket/logs/...?X-Amz-...",
    "uploadUrlExpiresAt": 1700005000,
    "encrypt": { "algorithm": "AES-256-GCM", "salt": "c29tZS1yYW5kb20tc2FsdA==" }
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `data.cmd` | string | 固定 `log_collect` |
| `data.collectId` | string | 采集任务唯一 ID，应答时**原样带回** |
| `data.objectKey` | string | 上传对象 key（后缀恒为 `.tar.gz`），设备端**原样回执**，不从 URL 拆 |
| `data.timeRangeStart` / `timeRangeEnd` | int64 | 可选；**设备端忽略**，不按时间窗切行 |
| `data.topicFiles` | string[] | 逻辑文件名清单（字典 basename，含 `.log`），按下发顺序处理 |
| `data.maxPacketSize` | int64 | **密文包上限**（含 nonce+tag 共 28 字节开销） |
| `data.uploadUrl` | string | 预签名 PUT URL |
| `data.uploadUrlExpiresAt` | int64 | URL 过期时间，Unix **秒** |
| `data.encrypt.algorithm` | string | 固定 `AES-256-GCM` |
| `data.encrypt.salt` | string | 本次 salt（base64 **原文**）；回显原样带回，仅派生密钥时 decode |

## 五、日志文件上传

### 5.1 收集规则

对每个 `topicFiles` 条目 `F`，在 `/var/log/topic/` 枚举：

- `F`（当前明文）
- `F.1` … `F.3`（未压缩归档，若存在）
- `F.1.gz` … `F.3.gz`（板端全局 `compress` 后的归档）

**有什么收什么**。写得慢、未触发轮转时可以只有单个 `.log`，这是正常情况。

`fileReport` **仍按逻辑名 `F` 一条**回报：`size` = 该名下纳入的全部物理文件磁盘字节之和。归档名不单独进 `fileReport`。

### 5.2 打包

- **永远**打成 `.tar.gz`（即使物理上只有一个 `.log`，tar 内也只有一项）。
- `objectKey` 后缀恒 `.tar.gz`；废止「按清单条目数猜 `.log` / `.tar.gz`」。

### 5.3 加密（AES-256-GCM + HKDF）

1. 先打 `tar.gz`，再对整包加密一次。
2. **HKDF**（RFC 5869，hash = SHA-256）  
   - IKM = `deviceSecret` **原始 UTF-8 字节**（与激活链路读入的同一 `std::string`；**不要**先 `sha256(secret)`）  
   - salt = 下行 base64 **decode 后的二进制**  
   - info = 写死 `snowx:iot:log-collect:enc:v1`  
   - 输出 32 字节 → AES-256 key  
3. nonce = 12 字节随机（每次采集独立），**前置**  
4. tag = 16 字节（GCM 128-bit），**后置**  
5. AAD = `v1:` + `collectId`（ASCII）  
6. 密文布局：`nonce(12) ‖ ciphertext ‖ tag(16)`

### 5.4 上传

- 对 `uploadUrl` 发 **HTTP PUT**，body = 密文。
- 必须带头：`Content-Type: application/octet-stream`（与 Oss/S3 预签名一致；不带或带错会 403）。
- 须在 `uploadUrlExpiresAt` 之前完成。

### 5.5 字节基准

| 字段 | 含义 |
|---|---|
| `fileSize`（回执） | **密文总字节** = `12 + n + 16`，与 headObject 一致 |
| `maxPacketSize` | **密文包上限**（含 28 字节开销） |
| `fileReport.size` | 明文磁盘贡献，只展示、不对账 |

超限：按 `topicFiles` 顺序纳入；某逻辑名（含其全部归档）纳入后密文将超限 → 整组跳过、`reason=size_exceeded`，继续后续；不截断、不分包。

### 5.6 全未收集

没有任何可上传内容（全 `not_found` / `empty`）→ **不 PUT**，回 `error` + `reason=NO_FILE_FOUND`。

## 六、设备回执 `command_ack`

Topic：`snowpod/{region}/{device_id}/cmd/ack`，QoS 1，`type=command_ack`，`req_id` 回传指令原值。

```json
{
  "v": 1,
  "type": "command_ack",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12346,
  "req_id": "7f3a1b2c4d5e6f7a8b9c0d1e2f3a4b5c",
  "data": {
    "cmd": "log_collect",
    "result": "accepted",
    "reason": null,
    "detail": {
      "collectId": "0f3a1b2c4d5e6f7a8b9c0d1e2f3a4b5c",
      "objectKey": "logs/SNOWPOD-A1B2C3D4/0f3a1b2c....tar.gz",
      "checksum": "",
      "fileSize": 12345,
      "encryptParams": "{\"algorithm\":\"AES-256-GCM\",\"salt\":\"c29tZS1yYW5kb20tc2FsdA==\"}",
      "fileReport": [
        { "file": "topic_mqtt_wire.log",  "collected": true,  "size": 4000 },
        { "file": "topic_print_flow.log", "collected": false, "reason": "not_found" }
      ]
    }
  }
}
```

### 6.1 `data.result` 三态

| result | 含义 | 设备端行为 |
|---|---|---|
| `accepted` | 收集并上传完成 | 携带完整 `detail`；**上传完成后**才发 |
| `rejected` | 拒绝执行（格式非法 / 已有任务进行中等） | `reason` + `detail.collectId` |
| `error` | 执行出错 | `reason` 闭集见 6.4，`detail.collectId` |

### 6.2 `detail`（result=accepted）

| 字段 | 必填 | 说明 |
|---|---|---|
| `collectId` | 是 | 原样回传 |
| `objectKey` | 是 | 原样回传下行 `data.objectKey` |
| `checksum` | 否 | 预留，当前填 `""` |
| `fileSize` | 是 | 密文总字节，须与 OSS 对象一致 |
| `encryptParams` | 是 | JSON **字符串**：`{"algorithm":"AES-256-GCM","salt":"<下行 base64 原文>"}` |
| `fileReport` | 是 | 逐文件；缺失或空数组 → `LOG_REPORT_MISSING` |

### 6.3 `fileReport[]`

| reason | 含义 |
|---|---|
| `not_found` | 当前文件与归档均不存在 |
| `empty` | 存在但全部 0 字节；`size=0` |
| `size_exceeded` | 纳入后超 `maxPacketSize`；`size`=明文实际值 >0 |

`not_found` 不填 `size`。设备端不要填 `unknown`。

### 6.4 任务级 `error.reason` 闭集

| reason | 含义 |
|---|---|
| `URL_EXPIRED` | 预签名已过期 |
| `PUT_FAILED` | HTTPS PUT 失败 |
| `DISK_FULL` | 临时目录/磁盘不足 |
| `ENCRYPT_FAIL` | 密钥派生或加密失败 |
| `NO_FILE_FOUND` | 无任何可上传内容 |
| `INTERNAL` | 其它内部错误（含全部因 size_exceeded 而空包） |

设备端不自造码。格式错误等走 `rejected` + `invalid_state`。

## 七、关键语义约束

1. **单设备单活动任务**：设备端同时只跑一个采集线程；忙时对新指令回 `rejected`。
2. **回执一次性**：accepted 为终态；不要先发空 accepted。
3. **fileReport 回全**：按下发清单逐条，失败也要带 reason。
4. **fileSize = 密文长度**。
5. **文件名逐字节对齐**字典（含后缀、大小写）。
6. **PUT Content-Type** 固定 `application/octet-stream`。
7. **salt 回显**用下行 base64 原文，不 decode 重编。

## 九、边界与排查

**未开放（阶段B）**：设备日志权威清单同步；设备不主动上报 manifest。

| 现象 | 排查方向 |
|---|---|
| 收不到指令 | topic / 认证 / 在线 |
| `LOG_REPORT_MISSING` | fileReport 空或截断；须上传完成后才 accepted |
| `LOG_CONTENT_MISMATCH` | fileSize ≠ 对象实际大小 |
| `INVALID_TOPIC_FILE` | 文件名与字典不一致 |
| PUT 403 | URL 过期，或 Content-Type 未带 / 与签名不一致 |

**联调**：先确保设备能上线并处理普通 cmd；再下发 `log_collect`。
