# 日志采集进度上报协议（冻结版）

版本：v1.1 · 状态：已冻结 2026-09-04

---

## 一、背景

日志采集链路完成后，平台侧只能看到任务终态（INSTRUCTED → VERIFYING → COMPLETED/FAILED），中间「设备正在上传」这一段没有信号。设备直传对象存储，数据不经过后端，平台拿不到实时进度。

本协议给设备加一条进度上报，让前端可展示上传进度（非历史回看）。进度不落库，只作瞬态信号。

## 二、设计总纲

- **终态 vs 进度二分**：终态回执（cmd_ack）是一次性、幂等、落库、不可丢的账本；进度是周期性、可丢、可乱序、有 TTL 的事件流。两条独立路径，互不混合。
- **进度绑定上传会话**：进度值「已传 80%」的语义是「这一次上传会话（attempt）内传了总字节的 80%」。进度属于 attempt，不属于任务 collectId。任务从下达到终态可能跨多次 attempt（断线重传），进度只活在单次 attempt 内。
- **报字节、平台算百分比**：设备报 transferredBytes（真值、单调），百分比是展示层算的。

## 三、传输通道

复用既有链路，新开专属 topic，不碰 cmd_ack。

| 环节 | 取值 |
|---|---|
| 设备上行 MQTT topic | `snowpod/{region}/{sn}/log_collect/progress`（QoS 1，retain false） |
| EMQX Rule Engine | 新增规则，路由上一步 topic → 下方 Kafka topic |
| Kafka topic | `iot.device.log_collect_progress`（新常量，3 partition，对齐其余 17 个设备 topic） |
| 消费方 | 新 consumer（独立，不复用 CmdAckConsumer） |

依据：本系统事件通道本就是「一业务一 topic」隔离（cmd_ack、ota、ota_manifest_request、heartbeat 各有专属 Kafka topic + 独立 consumer）。进度事件与终态回执语义相反、消息结构不同，必须独立 topic + 独立 consumer，严禁塞进 `iot.device.cmd_ack` 或 CmdAckConsumer。

## 四、消息封套

复用 §2 封套，`type` 取新值，`data` 结构如下：

```json
{
  "v": 1,
  "type": "log_collect_progress",
  "device_id": "SNOWPOD-XXXXXXXX",
  "ts": 1756960000000,
  "seq": 42,
  "data": {
    "collectId": "02f9...",
    "attemptId": "01J2X3Y4Z5A6B7C8D9E0F",
    "transferredBytes": 1234567,
    "totalBytes": 5000000
  }
}
```

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `type` | string | 是 | 固定 `log_collect_progress` |
| `seq` | int | 是 | 封套层序列号，仅观测（追踪消息有序性），**消费侧不拿它做去重判定** |
| `data.collectId` | string | 是 | 采集任务 ID，关联 `log_collect_task.collect_id`，定位「哪个任务」 |
| `data.attemptId` | string | 是 | 上传会话 ID，定位「哪一次上传」。固定 ULID，设备每次「从 0 开始一次新上传」生成新值 |
| `data.transferredBytes` | int64 | 是 | 已上传字节数，本 attempt 内单调递增（真值，取 max 的权威依据） |
| `data.totalBytes` | int64 | 是 | 上传产物总字节数（设备打包后已知），平台据此算百分比 |

## 五、单调性与会话口径

| 值 | 作用域 | 保证方式 |
|---|---|---|
| `transferredBytes` | attempt 内单调 | 上传是累积写字节，天然单调 |
| `attemptId` | 会话间单调 | ULID 定长 26 字符，字符串字典序 = 时间序 |
| `seq` | 仅观测 | 设备逐条递增即可，不参与任何大小比较、不做去重 |

**attemptId 生成口径（冻结后不改）**：只锁 ULID（禁止 UUIDv7 / UUIDv4）。ULID 定长 26 字符、无连字符，字符串字典序严格等于时间序；UUIDv7 带连字符、格式多样，字符串字典序不等于时间序，同毫秒随机后缀会让新旧颠倒。设备生成时，ULID 的 48bit 时间戳种子取 `max(now, lastAttemptTime)`（`lastAttemptTime` = 上一次 attemptId 的时间戳），随机部分每次重新生成，防 RTC/NTP 时钟回退。后端比较 attemptId 一律用字符串字典序。

**transferredBytes 聚合口径**：字节 = 单次 attempt 内「一个上传产物（单 `.log` 或单 `.tar.gz`）」的全量字节（单 PUT、不分片、不分包，一个 task 一个产物）。transferredBytes 是单次 PUT 流内随写随增的累计字节，不是跨 PUT 累计。**不承诺断点续传**：任何中断 = 该产物从 0 整包重传，进度随新 attemptId 归零；设备端不得脑补 Range 续传、不得在旧字节上续走。

## 六、消费规则

Redis key：`log_collect:progress:{collectId}`，value：`{attemptId, transferredBytes, totalBytes}`。TTL 采用滑动过期：**每次写入刷新 TTL**（默认 15 分钟），慢任务最后一段不会被固定窗口清空。

进度 consumer 处理顺序：

1. **状态门（写前查 task.status）**：仅 `INSTRUCTED` 允许写入 Redis；`VERIFYING` 及所有终态（`COMPLETED/FAILED/TIMEOUT/CANCELLED`）一律丢弃。`VERIFYING` 意味着上传已结束，进度在此阶段无意义，必须拒写，否则等于把 100% 回退到 90%。状态门直接查库（`log_collect_task` 单行、量级低，无缓存必要），不做缓存——缓存命中会绕过终态封顶（缓存 INSTRUCTED 后任务已转 COMPLETED，读旧缓存照样放行写回）。
2. **会话推进**（状态门通过后）：
   - 新消息 `attemptId` > 存值 → 新会话，重置基准，写入；前端可标注「重传（第 N 次尝试）」
   - 新消息 `attemptId` == 存值 → `transferredBytes` 取 max（天然幂等，重复投递无害，无需 seq 去重）
   - 新消息 `attemptId` < 存值 → 旧会话迟到消息，丢弃，记 metric 观测

**终态封顶**：靠状态门保证。终态落库后，迟到的进度消息在状态门被拒写，不会再写回 Redis、不会把前端已切的终态顶成进度值。

## 七、展示口径（查询接口）

前端进度条消费接口而非协议，返回结构冻结如下：

```
GET /log-collect/{collectId}/progress
→ { collectId, transferredBytes, totalBytes, percent, phase, status }
```

| 字段 | 含义 |
|---|---|
| `percent` | 平台算：transferredBytes / totalBytes，**clamp[0,100]** |
| `phase` | `uploading`（上传中，有进度值）/ `terminal`（已终态，前端不渲染进度，直接展示终态结果）/ `none`（任务非终态但无进度数据，前端降级显「暂无进度」中性态，不归 uploading、不归 terminal） |
| `status` | `phase=terminal` 时必返：task.status（`COMPLETED/FAILED/TIMEOUT/CANCELLED`），前端按它分「成功/失败」画面；`phase=uploading` / `phase=none` 时为空 |

- 越界钳制：transferredBytes > totalBytes 时 `percent` 钳 100，同时 WARN 落日志 + metric 告警，不静默吞掉（加密 padding / 设备多报都会顶出来，得可查）。
- 无进度 key：任务已终态 → 返回 `phase=terminal`；任务非终态（INSTRUCTED / VERIFYING）→ 返回 `phase=none`，前端降级显「暂无进度」中性态，不归 uploading、不归 terminal（杜绝无进度被误显成「上传中 0%」）。

## 八、边界与降级

1. **不落库**：进度只存 Redis 瞬态，不写表。历史回看不支持（已拍「不落进度、只落终态」）。
2. **终态封顶**：见六、七，状态门 + phase=terminal 双保证。
3. **旧固件降级**：不报进度的老设备，平台优雅降级为「无进度条」：任务进行中显「暂无进度」（none）、终态显终态结果，是一等兼容设计，作一条验收用例。
4. **刷新闪空**：不落库 + 纯 Redis，用户刷新瞬间进度条可能闪空、等设备下一拍恢复，前端做「进入先拉一次现值 + 兜底等下一拍」。

## 九、验收卡点（对齐 QA 用例册）

- collectId 定位任务：进度消息必须带 collectId，前端不得分不清任务。
- 报字节、平台算百分比：不出现「第几个包 / 共几个包」的冗余口径。
- 终态封顶：进度不停在中间值骗人；终态后迟到进度消息不写回（状态门拒写）。
- 单调性：断点重传进度条不回退。
- attemptId 重启不回退：上传中断电重启，进度条能从 0 正常重爬，不被旧峰值吞掉。
- 越界钳制：transferredBytes > totalBytes 时百分比钳 100 + 告警，不渲出 >100%。
- TTL 滑动续期：慢任务进度不被固定窗口提前清空。
- 旧固件降级：无进度条，进行中显「暂无进度」（none）、终态显终态结果。

## 十、字段来源指认

- 任务实体：`iot-dal LogCollectTask`（collectId、status、fileSize 等已存在）。
- 终态回执路径：`iot-command-downlink CmdAckConsumer.handleLogCollectAck → LogCollectTaskServiceImpl.onCollectAck`（既有，本协议不改动）。
- 状态机参考：`OtaProgressConsumer` 是状态跃迁语义（setIfAbsent 去重），本协议进度是字节取 max 语义，两者不同，seq 去重不适用。
- 本协议新增：MQTT 上行 topic、EMQX 规则、Kafka topic `iot.device.log_collect_progress`、新 consumer、进度查询接口，均待冻结后开发。
