# 视频播放模块设计文档

## 1. 视频播放模块整体方案设计（综合落地）

`操作说明.txt` 给出的模块级设计，结合上述三种方案，设计路径如下。

### 1.1 直播播放（实时画面）

1. 设备端需要部署 RTSP 服务器（MediaMTX 或 live555），需考虑打印与录像回放并存时的性能占用等问题。
2. 设备开始打印时，通过 **HTTP print_start 协议回传拉流地址**（如 `rtsp://host:8554/liveX` 或 HLS/WebRTC 地址）到上位机/云端。
3. 桌面软件根据回传地址用内置播放器（如 VLC/FFmpeg/WebRTC）播放。
4. 手机端如有需求，可同步获取同一拉流地址观看（HLS 或 WebRTC 具备网络穿透能力，适合手机端）。

```
[设备开始打印] --> [HTTP 回复拉流地址] --> [桌面端播放]
                                        --> [手机端播放(可选)]
```

### 1.2 历史回放（已实现两种方案）

**方案 1：HTTP Server 直接回放 MP4 文件**
- 请求 `http://127.0.0.1:8081/111.mp4`，HTTP Server 在根目录下按路径推送文件内容；如基于nodes.js或者其他自行开发的httpserver，需要支持Range参数，实现seek跳转功能。
- 客户端（浏览器/播放器）**边下边播**；
- 必须支持 `Range` 请求头，才能实现 seek 跳转（断点续传式定位）；
- 优点：随时点播任意 MP4，只需 MP4 的时长信息写在文件头部（moov atom 前置，`faststart`）；下载能力本就是必需功能。
- 缺点：文件需自行录制保存，无自动分段/检索，需要httpserver实现录像查询：（按相关参数传入如日期参数；录像类型），以及录像下载接口

**方案 2：MediaMTX 自动录像回放**
- 推流即自动分段落盘，支持查询与回放；
- 优点：自动录像、配置即用；
- 缺点：文件名与推流路径绑定，无法区分录像类型（报警/异常/正常），仅能按 path 区分。

### 1.3 综合选型

> **RTSP 服务器层**：MediaMTX 作 RTSP 流服务器（或采用 live555）；
> **录像回放/查询/下载层**：自研 HTTP Server 承担，弥补 MediaMTX 无法标注录像类型的能力缺失。

一种可选组合为「**MediaMTX 负责流 + 自研 HTTP 负责录像管理**」的混合架构（对应方案 C），并在录像文件名/元数据中写入类型标签（正常/报警/异常）。


## 2. 结论与路径

1. **直播**：MediaMTX 作 RTSP 服务器，打印开始 HTTP 回传拉流地址，桌面/手机按需拉流（手机端可采用 WebRTC/HLS）。
2. **回放（复用现有）**：方案 2——MediaMTX 自动录像 + `:9996/get` 按时间回放 + 客户端 `playbackRate` 倍速 + 重拉实现 seek。
3. **回放（自研推流管理）**：方案 1——MediaMTX 仅作 RTSP 服务器 + 自研 HTTP 推流/管理程序，由推流端统一实现倍速/暂停/seek，并用元数据索引区分录像类型。
4. **录像类型**：以 path 区分或建立元数据索引，解决「报警/异常/正常」无法标注的痛点。

## 3. 功能拓展分析

1. **需求展望拓展**：将来可能拓展更多功能，如回放正在录制的录像文件，由于此时文件尚未完成录制，mp4信息不完整，回放时httpserver对文件需要做特殊处理才可能完成播放，所以需要额外的处理。
2. **打印历史视频安全性提升**：需要在7*24小时条件下完成录像并存储，随时回放查看，这需要打印设备集成完整 NVR 功能，系统复杂性将显著提升。
