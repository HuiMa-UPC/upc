# 视频流对接说明（v0.5）

> 角色：App 端 · 云端（后端）· 设备端（SoC）
> 依据：《设备通信协议-数据结构定义 v0.5》《mediamtx 部署规范》
> 状态：草案，待 M0 协议冻结前与各端收口

---

## 架构概览

视频数据**全存设备端，不上云**。信令走 MQTT（`cmd` / `cmd/ack`），媒体流走 **RTSP over TCP**（interleaved 模式）。云侧部署 mediamtx 作为 RTSP Broker。

```
          信令（MQTT via EMQX）
App ─────── Cloud API + MQTT ──────────── Device
                   │                         │
                   │                  RTSP ANNOUNCE
                   │                  (设备主动推流，出站 TCP)
                   │                         │
           ┌───────▼────────┐                │
           │   mediamtx     │◄───────────────┘
           │   relay        │
           └───────┬────────┘
                   │ RTSP PLAY (App 拉流)
                   ▼
                  App
```

**网络路径说明：**

| 场景 | 路径 | 说明 |
|------|------|------|
| 局域网 | App → Device RTSP (:8554) 直连 | App **自行判断**是否与设备同局域网；若可通则直连，**不经过云端接口**，云端不介入此路径 |
| 远程（走云端接口） | Device → mediamtx → App | 调用云端 `/streams` 接口时，**固定走 relay**；云端只返回 `pull_url`，不涉及局域网地址 |

全程 **RTSP over TCP（interleaved）**，信令与媒体数据复用同一条 TCP 连接，无需额外 UDP 端口，防火墙友好。

## 一、实时流

### 流程图

```
App                    Cloud                    Device
 │                        │                        │
 │─1. POST /streams/{id}/live/start ──────────────►│
 │◄─2. { pull_url, expires_at } ──────────────────│
 │                        │─3. MQTT start_rtsp_push►│  ← fire-and-forget，不等 ACK
 │                        │   (push_url, push_token │
 │                        │    transport=tcp)       │
 │                        │                        │─── 启动 GStreamer
 │                        │                        │    RTSP ANNOUNCE
 │                        │                        │───→ mediamtx relay
 │                        │◄─4. cmd/ack ───────────│  ← 异步到达，仅用于错误上报
 │                        │                        │
 │  RTSP PLAY → pull_url (mediamtx relay)          │
 │◄── 视频流 via relay ────────────────────────────│
```

### 各端职责

#### App 端

1. **请求开流**
   ```
   POST /api/v1/streams/{device_id}/live/start
   Authorization: Bearer {userToken}
   ```
   云端返回：
   ```json
   {
     "pull_url": "rtsp://relay.snowx.com:8554/live/SNOWPOD-A1B2C3D4?token=yyy",
     "expires_at": 1753232400
   }
   ```
   > 云端固定返回 relay 地址；若 App 在调用接口前已判断局域网可通，则不需调用此接口，直接与设备直连即可。

2. **RTSP 播放**（Flutter，强制 TCP transport）
   ```dart
   // pubspec.yaml 新增：
   // media_kit: ^1.x
   // media_kit_video: ^1.x
   // media_kit_libs_video: ^1.x  ← 包含 libmpv，支持 RTSP/TCP

   final player = Player();
   final controller = VideoController(player);

   player.open(Media(pull_url));
   // media_kit 底层 libmpv 默认强制 TCP，无需额外参数
   ```

3. **停止流**：调用 `DELETE /api/v1/streams/{device_id}/live`，云端下发 `stop_rtsp_push`

#### 云端

1. **开流**（`POST /streams/{device_id}/live/start`）：
   - 生成 `push_token`（设备用）和 `pull_token`（App 用），有效期 30 min
   - `push_url = rtsp://relay:8554/live/{device_id}?token={push_token}`
   - `pull_url = rtsp://relay.snowx.com:8554/live/{device_id}?token={pull_token}`
   - 通过 EMQX 下发 MQTT `start_rtsp_push` 至设备（**fire-and-forget，立即返回 `pull_url` 给 App，不等待设备 ACK**）

2. **停流**（`DELETE /streams/{device_id}/live`）：下发 `stop_rtsp_push`，撤销两个 token

3. **不参与媒体传输**，只做信令调度和 token 管理

#### 设备端

1. 收到 `start_rtsp_push`（`stream_type=live`）后：
   - 启动摄像头（如未启动）
   - 调用 GStreamer pipeline 向 `push_url` 推流：
     ```
     v4l2src → 硬件 H.264 编码 →
     rtspclientsink location={push_url} protocols=tcp
     ```
   - 回 `cmd/ack`（`result=accepted`；推流启动失败时 `result=error, reason=encoder_error`）

2. 收到 `stop_rtsp_push`（`stream_type=live`）后断开推流 pipeline

## 二、录像回放

### 流程图

```
App                    Cloud                    Device
 │                        │                        │
 │─1. POST /recordings/list?page=1 ──────────────►│
 │◄─2. { reqId }─────────────────────────────────│
 │                        │─3. MQTT                 │
 │                        │   recording/list_request►│
 │                        │◄─4. recording/list_response (异步)
 │                        │   → Kafka → Redis       │
 │─5. GET /recordings/result/{reqId}（轮询）───────►│
 │◄─6. { total, page, page_size, items }──────────│
 │─7. 用户选择录像          │                        │
 │─8. POST /streams/{id}/recording/start ──────────►│
 │     Body: { recording_id, seek_s }              │
 │◄─9. { pull_url, expires_at }───────────────────│
 │                        │─10. MQTT start_rtsp_push►│  ← fire-and-forget，不等 ACK
 │                        │    (recording, id, seek_s│
 │                        │     push_url, push_token)│
 │                        │                        │─── FFmpeg -re 读文件
 │                        │                        │    RTSP ANNOUNCE
 │                        │                        │───→ mediamtx relay
 │                        │◄─11. cmd/ack ───────────│  ← 异步到达，仅用于错误上报
 │─12. RTSP PLAY → pull_url（播放录像）              │
```

**Seek（跳播）**：
```
App → POST /streams/{device_id}/recording/seek { seek_s: 120 }
Cloud → MQTT start_rtsp_push（新 req_id，seek_s=120）
Device → 终止旧 FFmpeg 进程，从第 120s 重新推流
App → 重连 RTSP 播放器（pull_url 不变）
```

### 各端职责

#### App 端

1. 获取录像列表（见§四）
2. **请求开流**：`POST /streams/{device_id}/recording/start`，Body：`{ recording_id, seek_s: 0 }`
3. 使用响应中的 `pull_url` 连接 mediamtx relay 播放
4. **Seek**：调用 seek 接口，重连播放器
5. **停止**：`DELETE /streams/{device_id}/recording`

#### 云端

同实时流，额外将 `recording_id`、`seek_s` 透传给设备

#### 设备端

1. 收到 `start_rtsp_push`（`stream_type=recording`）后：
   - 定位录像文件（按 `recording_id`）
   - 启动 FFmpeg 推流：
     ```
     ffmpeg -re -ss {seek_s} -i /recordings/{recording_id}.mp4 \
            -c copy -f rtsp -rtsp_transport tcp {push_url}
     ```
   - 回 `cmd/ack`（`result=accepted`；文件不存在时 `result=rejected, reason=recording_not_found`；编码器失败时 `result=error, reason=encoder_error`）

2. 收到新 `start_rtsp_push`（Seek）时，先 kill 当前 FFmpeg 进程，再启动新进程

## 三、快照

无需开启 RTSP 流，全程 MQTT。

**请求**（下行 `cmd`，含 §二 封套）：
```json
{ "...", "req_id": "uuid", "data": { "cmd": "snapshot" } }
```

**应答**（上行 `cmd/ack`，含 §二 封套）：
```json
{
  "v": 1,
  "type": "command_ack",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12346,
  "req_id": "uuid",
  "data": {
    "cmd": "snapshot",
    "result": "accepted",
    "detail": { "snapshot_data": "/9j/4AAQSkZJR...", "captured_at": 1753228800000 }
  }
}
```

`snapshot_data`：base64 JPEG，建议分辨率 ≤ 1280×720。MQTT broker 须配置 `max_packet_size ≥ 256 KB`。

## 四、录像列表

录像文件保存在**设备本地**，不上云。获取列表有两条路径：

### 云端中转（远程/默认路径）

App 通过云端 HTTP API 请求，云端经 EMQX 转发指令，结果经 Kafka 异步回传。

```
① App  → POST /api/v1/commands/devices/{device_id}/recordings/list
          ?page=1&pageSize=20
         云端立即返回 { "reqId": "..." }，不阻塞

② Cloud → EMQX → Device  MQTT recording/list_request（§9.1）

③ Device → MQTT recording/list_response
          → EMQX Rule → Kafka iot.device.recording_list_response
          → Redis（key: cmd:rec_list:{reqId}，TTL 5 min）

④ App  → GET /api/v1/commands/devices/{device_id}/recordings/result/{reqId}
         结果已到达 → 200 + { total, page, page_size, items }
         尚未到达/已过期 → 404，稍后重试
```

### 局域网直连（LAN 场景，不走云端）

App 判断与设备处于同一局域网时，直接访问设备本地 HTTP 服务，同步返回，无需经云端，无需轮询：

```
GET http://{device_ip}:{port}/recordings?page=1&page_size=20
→ 同步返回 { total, page, page_size, items }
```

> 设备本地 HTTP 端口和路径由 SoC 侧确定（与缩略图直连接口对齐）。

### MQTT 消息格式（SoC 端参考）

**请求**（`recording/list_request` 下行，含 §二 封套）：
```json
{ "...", "req_id": "uuid", "data": { "page": 1, "page_size": 20 } }
```

**应答**（`recording/list_response` 上行，含 §二 封套）：
```json
{
  "v": 1,
  "type": "recording_list_response",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12347,
  "req_id": "uuid",
  "data": {
    "total": 42,
    "page": 1,
    "page_size": 20,
    "items": [
      {
        "recording_id": "job-20260723-001",
        "job_id":        "job-20260723-001",
        "started_at":    1753228800000,
        "duration_s":    14400,
        "size_bytes":    2147483648
      }
    ]
  }
}
```

## 五、异常处理

| 场景 | 处理方式                                                                              |
|------|-----------------------------------------------------------------------------------|
| 设备离线 | `start_rtsp_push` 等待 `cmd/ack` 超时（10s）→ 返回 503，App 提示"设备不在线"                      |
| 推流启动失败 | `cmd/ack.result=error, reason=encoder_error` → App 提示重试                           |
| relay 推流中断 | App RTSP PLAY 连接断开 → 重新调用 start 接口                                                |
| 录像不存在 | `cmd/ack.result=rejected, reason=recording_not_found` → App 提示                    |
| 重复推流 | `cmd/ack.result=rejected, reason=push_already_active` → 云端先发 `stop_rtsp_push` 再重试 |
| token 过期 | 重新调用 start 接口，获取新 `pull_url` + token                                              |
| 局域网探测超时 | 静默降级至 rela基于y，无需用户感知                                                              |

## 六、关键约定

1. **全程 TCP**：RTSP transport 固定 `tcp`（interleaved）；设备推流和 App 拉流均强制 TCP，彻底避免 UDP NAT 问题
2. **实时流 + 录像并行**：允许同时存在一路 `live` + 一路 `recording`，路径独立互不影响
3. **Seek 通过重推实现**：重发 `start_rtsp_push`（新 `seek_s`），设备重启推流进程，App 重连 RTSP 播放器
4. **relay 自动回收**：设备断开 RTSP ANNOUNCE 后，mediamtx 自动关闭对应 path；App 的 RTSP PLAY 随即断开
5. **push_token / pull_token 分离**：push_token 仅设备使用（mediamtx publish 权限），pull_token 仅 App 使用（read 权限），有效期均 30 min
6. **仅 App 端播放**：Web 浏览器不支持原生 RTSP，本协议仅面向原生移动 App
