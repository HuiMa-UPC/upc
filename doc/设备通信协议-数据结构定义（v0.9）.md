> 角色：社区技术部 · 数据结构决策方

> 依据：《设备通信协议骨架（v0.1 草案）》
> 告警章节更新：2026-09-22，按当前 alarm 实现及 [SOC—云端告警契约](../spec/alarm/soc-alarm-contract-v1.md) 修订；设备能力仍须双方联调确认。

## 一、MQTT Topic 命名

所有 topic 以 `snowpod/{region}/{device_id}/` 为前缀。

| 方向 | Topic | QoS | 说明 |
|------|-------|-----|------|
| 上行 | `snowpod/{region}/{device_id}/telemetry/{group}` | 0/1 | 遥测，按功能域分组，高频组 QoS0 |
| 上行 | `snowpod/{region}/{device_id}/state` | 1 | 状态变更（mode / substate 变化时发送）|
| 上行 | `snowpod/{region}/{device_id}/event` | 1 | 既有作业/通用事件，不接入设备主动告警中心 |
| 上行 | `snowpod/{region}/{device_id}/alarm/report` | 1 | 设备单条告警、完整快照、源状态；retain=false |
| 下行 | `snowpod/{region}/{device_id}/alarm/ack` | 1 | 云端持久化接收回执；retain=false |
| 上行 | `snowpod/{region}/{device_id}/cmd/ack` | 1 | 指令应答 |
| 上行 | `snowpod/{region}/{device_id}/ota/progress` | 1 | OTA 进度上报 |
| 上行 | `snowpod/{region}/{device_id}/heartbeat` | 1 | 设备心跳（版本/能力周期上报，默认 30min，见 §8.3）|
| 上行 | `snowpod/{region}/{device_id}/recording/list_response` | 1 | 录像列表应答 |
| 下行 | `snowpod/{region}/{device_id}/cmd` | 1 | 指令下发（含流控指令 snapshot / start_rtsp_push / stop_rtsp_push）|
| 下行 | `snowpod/{region}/{device_id}/ota/notify` | 1 | 通知新固件版本 |
| 下行 | `snowpod/{region}/{device_id}/recording/list_request` | 1 | 请求录像列表 |

**字段规则：**
- `{region}`：`cn`（国内）/ `intl`（国际），云侧路由与 ACL 隔离
- `{device_id}`：激活时云侧分配，格式 `SNOWPOD-{8位大写十六进制}`，例：`SNOWPOD-A1B2C3D4`

## 二、消息封套（通用）

遥测、状态、作业事件等既有消息共用以下顶层结构。设备告警 `alarm.single` / `alarm.snapshot` / `alarm.status` 使用 §5.3 的专用消息头，以 UUID 和十进制字符串序号标识消息，不使用本节 `seq`；`alarm.receipt` 使用 §5.7 的回执头。

```json
{
  "v": 1,
  "type": "telemetry",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "req_id": "7f3a1b2c-...",
  "data": {}
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `v` | int | 是 | schema 版本，当前为 `1`，字段新增时递增，接收方忽略未知字段 |
| `type` | string | 是 | 见下方枚举 |
| `device_id` | string | 是 | 设备唯一 ID |
| `ts` | int64 | 是 | 消息产生时刻，Unix 毫秒时间戳，NTP 对时后可信 |
| `seq` | uint32 | 是 | 单调递增序号，设备重启后可归零；配合 `ts` 做去重与丢包检测 |
| `req_id` | string | 条件 | `type=command` 时必填；`cmd/ack` 回传同值；其余可选 |
| `data` | object | 是 | 业务体，结构由 `type` 决定 |

`type` 枚举：

| 值 | 方向 | 说明 |
|----|------|------|
| `telemetry` | 上行 | 遥测数据 |
| `state` | 上行 | 设备状态变更 |
| `event` | 上行 | 既有作业/通用事件，不用于设备主动告警 |
| `alarm.single` | 上行 | 单条设备 CONDITION / EVENT，见 §5.4 |
| `alarm.snapshot` | 上行 | 完整 CONDITION 快照，见 §5.5 |
| `alarm.status` | 上行 | 源会话、能力、链路和缺口信息，见 §5.6 |
| `alarm.receipt` | 下行 | 云端持久化接收回执，见 §5.7 |
| `command` | 下行 | 指令 |
| `command_ack` | 上行 | 指令应答 |
| `ota_notify` | 下行 | 固件版本通知 |
| `ota_manifest_request` | 上行 | OTA manifest 领取请求 |
| `ota_manifest` | 下行 | OTA manifest 领取应答 |
| `ota_progress` | 上行 | OTA 进度 |
| `ota_check` | 上行 | 检查更新请求（pull） |
| `ota_check_ack` | 下行 | 检查更新应答（三态） |
| `heartbeat` | 上行 | 设备心跳（版本/能力周期上报）|
| `recording_list_request` | 下行 | 请求录像列表 |
| `recording_list_response` | 上行 | 录像列表应答 |

## 三、遥测消息（上行）

`data.group` 标识遥测组，与 topic 末段一致。

### 3.1 `chamber` — 仓内环境（打印中 1–2s；待机 30s）

```json
{
  "v": 1,
  "type": "telemetry",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "data": {
    "group": "chamber",
    "pm25": 12.5,
    "pm1_0": 8.6,
    "pm10": 23.4,
    "humidity": 52.3,
    "pressure_1": 101.3,
    "o2_ppm": 7200,
    "ntc_c": 118.0
  }
}
```

| 字段 | 类型 | 单位 | 安全关键 |
|------|------|------|---------|
| `pm25` | float | μg/m³ | 否（仓内实时）|
| `pm1_0` | float | μg/m³ | 否（仓内实时）|
| `pm10` | float | μg/m³ | 否（仓内实时）|
| `humidity` | float | % | 否（仓内相对湿度）|
| `pressure_1` | float | kPa | 否（舱内 1 压力）|
| `o2_ppm` | int | ppm | **是**，超 `o2_threshold_ppm` 触发 O2_HIGH |
| `ntc_c` | float | °C | **是** |

> 原始编码：`pm1_0` / `pm10` / `humidity` / `pressure_1` 设备侧均为 INT16 小端（LE），分辨率 0.1（湿度 0.1%、舱压 0.1kPa、PM 0.1μg/m³）；网关/固件按 ×0.1 缩放后以十进制上报本 JSON 字段，后端不解析二进制。量程：湿度 0–100%，PM1.0/PM10 0–1000 μg/m³（PM 传感器典型量程，待 SoC 确认），舱内压力 0–200 kPa（典型常压 101.3 附近，待 SoC 确认）。

### 3.2 `chamber_ext` — 仓外环境（5–10s）

```json
{
  "v": 1,
  "type": "telemetry",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "data": { "group": "chamber_ext", "pm25": 8.2 }
}
```

### 3.3 `powder` — 粉料（事件驱动 + 每 30s）

```json
{
  "v": 1,
  "type": "telemetry",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "data": {
    "group": "powder",
    "cartridges": [
      { "slot": 1, "rfid_id": "A1B2C3D4E5F6", "rfid_valid": true, "lock_hall": true, "ball_valve_hall": false }
    ],
    "cartridge_weight_g": [
      { "slot": 1, "value": 1250.0 }
    ],
    "funnel_weight_g": [
      { "funnel_id": 1, "value": 320.5 },
      { "funnel_id": 2, "value": 315.0 }
    ],
    "low_level": [
      { "slot": 1, "triggered": false }
    ]
  }
}
```

`slot` 取值 1–5（对应 5 粉盒）；`funnel_id` 取值 1–5（默认与粉盒数量一致，待 SoC 确认实际漏斗数量）。`rfid_id` 只上报 ID/校验结果，不上报密钥。低粉位可作为规则配置的业务依据；是否生成规则告警以启用规则及实际可提取的数值指标为准，不代表设备必须上报字符串码 `POWDER_LOW`。

### 3.4 `motion` — 运动（打印中按层/事件）

```json
{
  "v": 1,
  "type": "telemetry",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "data": {
    "group": "motion",
    "z_limit": [
      { "z_limit_id": 1, "triggered": false },
      { "z_limit_id": 2, "triggered": false }
    ],
    "blade_limit": [
      { "blade_limit_id": 1, "triggered": false },
      { "blade_limit_id": 2, "triggered": false }
    ],
    "stall_guard": [
      { "axis": "z1", "triggered": false, "raw": 120 },
      { "axis": "blade", "triggered": false, "raw": 95 }
    ]
  }
}
```

运动异常的设备主动告警按 §五 上报 MCU 数字码；遥测规则是否触发由实际指标和规则配置决定。`z_limit_id` / `blade_limit_id` 各取值 1–2（对应双限位传感器，待 SoC 确认）。`axis` 命名由 SoC 侧确认，最多 6 个轴。

### 3.5 `dust` — 除尘系统（每 5s）

```json
{
  "v": 1,
  "type": "telemetry",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "data": {
    "group": "dust",
    "cyclone_ntc_c": 42.0,
    "filter_ntc_c": 38.5,
    "fan_inlet_ntc_c": 35.0,
    "chamber_ntc_c": [118.0, 119.5],
    "chamber_ir_temp_c": [120.0, 121.5],
    "exhaust_o2_ppm": [7100, 7150],
    "fan_rpm": 2800,
    "fan_current_a": 1.2
  }
}
```

`filter_ntc_c` 超阈值触发 `FILTER_OVERTEMP`。`exhaust_o2_ppm` 两路冗余，任一超标触发 `O2_HIGH`。

### 3.6 `door` — 门/对接（事件驱动，状态变化即报）

```json
{
  "v": 1,
  "type": "telemetry",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "data": {
    "group": "door",
    "outer_door": { "d2f": true, "hall": true, "locked": true },
    "inner_door": { "d2f": true, "hall": true },
    "transfer_box": { "docked": false }
  }
}
```

`true` 表示关闭/锁定/已对接。双冗余（D2F + 霍尔）不一致时，设备主动告警按 §五 上报设备字典中的数字码，不使用本节另造的字符串码。

### 3.7 `power` — 电源（每 10s）

```json
{
  "v": 1,
  "type": "telemetry",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "data": {
    "group": "power",
    "rails": [
      { "name": "24V", "voltage_v": 24.1, "current_a": 3.5 },
      { "name": "12V", "voltage_v": 12.0, "current_a": 0.8 },
      { "name": "5V",  "voltage_v": 5.02, "current_a": 1.2 }
    ]
  }
}
```

`name` 的实际轨道命名与个数由 SoC（N7 电源管理板）确认。

### 3.8 `safety` — 安全联锁（事件驱动 + 每 5s 心跳）

```json
{
  "v": 1,
  "type": "telemetry",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "data": {
    "group": "safety",
    "estop_triggered": false,
    "heartbeat_seq": 1234,
    "subsystems": {
      "laser":  "ok",
      "galvo":  "ok",
      "motion": "ok",
      "dust":   "ok",
      "door":   "ok",
      "o2":     "ok"
    }
  }
}
```

`subsystems` 每项取值：`ok` / `warn` / `fault`。此组为**只读**，云侧/App 不可通过指令修改安全联锁状态。急停的设备主动告警按 §五 上报对应数字码及 severity；本节布尔字段不等于已生成云端规则告警。

## 四、状态消息（上行）

`mode` 或 `substate` 变化时即刻上报至 `state` topic；设备上线后主动上报一次完整状态。

```json
{
  "v": 1,
  "type": "state",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "data": {
    "mode": "printing",
    "substate": "layer_printing",
    "since": 1753228800000,
    "job": {
      "job_id": "job-20260723-001",
      "layer": 42,
      "total_layers": 500,
      "progress_pct": 8,
      "eta_s": 14000,
      "started_at": 1753228800000
    },
    "health": {
      "laser":  "ok",
      "galvo":  "ok",
      "motion": "ok",
      "dust":   "ok",
      "safety": "ok"
    }
  }
}
```

### `mode` 枚举

| mode | 说明 | 可下发的高层意图 |
|------|------|----------------|
| `provisioning` | 首次开机/配网/激活绑定 | — |
| `idle` | 空闲待机 | `start_print`、`start_selftest`、`sleep` |
| `purge` | 洗气（制氮置换 O₂） | `cancel` |
| `printing` | 激光扫描+铺粉+Z 循环 | `pause`、`resume`、`cancel` |
| `unload` | 取件（吸粉→PM2.5 联锁→解锁外门） | `request_unlock` |
| `maintenance` | 维护（换件/清洁/校准） | 视具体维护项 |
| `updating` | 固件升级（OTA，§八） | — |
| `selftest` | 自检 | — |
| `sleep` | 节能睡眠 | `wake` |
| `estop` | 急停（物理触发，不可远程复位） | — |

### `substate` 枚举（按 mode 分组）

| mode | substate 值 | 说明 |
|------|------------|------|
| `provisioning` | `awaiting_wifi` / `connecting` / `activating` / `binding` | 配网各阶段 |
| `idle` | `ready` / `not_ready` / `job_loading` | 可开始打印 / 条件未满足 / 已接受 start_print 正在下载作业文件 |
| `purge` | `checking_door` / `purging_o2` / `stabilizing` | 检查门→置换→稳定 |
| `printing` | `heating` / `homing` / `layer_printing` / `pausing` / `paused` / `cooling` | 打印全阶段 |
| `unload` | `dust_extracting` / `waiting_pm25` / `unlock_allowed` / `unloading` | 取件全阶段 |
| `maintenance` | `cleaning` / `calibrating` / `replacing_filter` / `replacing_powder` / `service_lock` | 维护类型 |
| `updating` | `downloading` / `verifying` / `applying` / `rolled_back` | 固件下载 / 校验 / 刷写 / 回滚（§8.2） |
| `selftest` | `sensor_check` / `actuator_check` / `communication_check` / `safety_check` | 自检阶段 |
| `sleep` | `sleeping` | 睡眠中 |
| `estop` | `triggered` / `local_reset_required` | 急停已触发 / 等待本地复位 |

> **`updating` 附注**：substate 仅列持续态。`completed`（刷写完成→重启→`idle`）与 `failed`（回滚→`idle`，失败原因见 §8.2 `ota_progress.error_code`）是离开 `updating` 的出口，不占 substate。

`since`：进入当前 mode 的时间戳（毫秒）。`job` 子对象仅在 `mode` 为 `purge` / `printing` / `unload` 时携带（对应同一个作业的生命周期）；其余 mode 下省略或为 `null`。

**`job` 子对象字段：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `job_id` | string | 作业 ID，与 `start_print` 中一致 |
| `layer` | int | 当前已完成层数（0 = 打印尚未开始）|
| `total_layers` | int | 总层数（0 = 模型解析中，尚未确定）|
| `progress_pct` | int | 0–100，`layer / total_layers × 100`，设备端计算 |
| `eta_s` | int | 估计剩余秒数；`null` = 尚无法估算 |
| `started_at` | int64 | 作业开始时间戳（毫秒），`start_print` 被接受时记录 |

## 五、设备主动告警与事件协议

本节取代原 `event + code(string) + active(bool) + detail(object)` 告警模型。设备告警使用 MCU 事件码及独立 detail 码；原 26 个字符串业务码不作为 MCU 告警字典，也不据此转换设备码。既有作业消息 `/event` 及其记录链路仍见 §11.4，不能把作业通知与本节 EVENT 混为一类。

告警中心分两条来源：设备上报经 `DeviceAlarmConsumer` 形成 `source=device`；遥测经规则引擎形成 `source=rule`。两者独立去重、独立恢复，设备快照不会清除规则告警。

本节只定义 SOC 与云端的对接数据，不规定 SOC 自动快照、串口分片、缓存或调度实现，不增加手动同步、rebind 或远程 RESET 接口。完整联调清单见 [SOC—云端告警契约](../spec/alarm/soc-alarm-contract-v1.md)。

### 5.1 告警字段和状态含义

| 字段 | 类型与含义 |
|---|---|
| alarm_code | 0–65535 的整数，事件表 code |
| severity | 0–255 的整数；已知值 1 INFO、2 WARNING、3 ERROR、4 CRITICAL |
| state_mask | 0–255 的整数；bit0 active、bit1 latched、bit2 EVENT |
| clear_mode | 0–255 的整数；0 AUTO、1 RESET、2 POWER_CYCLE、3 NONE；仅展示 |
| detail | 0–4294967295 的整数；detail code，歧义见§5.9 |

**active/latched 是两个独立布尔位，不是“0 告警、1 消警”。**

| mask 低三位 | 云端解释 | 当前 CONDITION |
|---|---|---|
| 000 | NORMAL：生命周期结束 | 无 |
| 001 | ACTIVE：故障中，未锁存 | 有 |
| 010 | RTN_LATCHED：条件已恢复，但仍锁存 | 有 |
| 011 | ACTIVE：故障中且锁存 | 有 |
| 1xx | EVENT：一次性事件 | 不改变 CONDITION |

bit2 优先。EVENT 同时置 active/latched 时保留原始组合，仍按 EVENT。保留位 bit3–7 忽略语义、保留原值。severity 非零不代表告警未恢复；clear_mode 不参与云端自动消警。

### 5.2 身份与顺序：完全由 SOC 保证

云端只使用一套 SOC 消息身份，不再要求或使用 mcu_boot_id、source_seq；依赖它们的 last_source_seq、lost_source_ranges、metadata_source_seq 和 capabilities 也从对接结构移除。旧报文携带这些额外字段（包括 null）不会因此拒绝，但云端不解释其顺序语义；重传时仍必须保持整个载荷不变。

| 字段 | SOC 必须保证的语义 |
|---|---|
| message_id | UUID，一条消息的唯一身份，同消息重传不变 |
| stream_id | UUID，一条 SOC 上报流的身份；重连且保留顺序时继续使用，无法保持序号/采集顺序时换流 |
| report_seq | 同流内所有 single、snapshot、status 共用的递增序号，从字符串 "1" 开始；每个新消息占一个序号 |
| 快照 report_seq=W | 完整状态是在 W 这个顺序位置采集；必须包含同流中序号小于 W 的条件变化，不包含 W 之后的变化 |

SOC 负责识别并过滤 MCU 重传/旧串口消息，不能把同一个源事件重新包装成不同上云身份。云端不再提供 MCU 源事件的第二层去重。单报、快照、状态共用编号；序号跳号不导致云端等待，明确知道的数据丢失通过 lost_report_ranges 报告。

快照与单报的采集顺序必须和编号一致：不能在新告警之后把旧快照编号为更大序号。SOC 负责确保快照完整且一致，不能混合不同采集时刻的片段冒充一个状态。该要求是接口语义，不规定内部实现或自动快照时机。

无法维持这套顺序（例如 SOC 状态丢失，或 MCU 重启后旧缓存无法正确辨别）时换 stream_id；新流完整快照用于重新校准。普通 MCU 重启不要求另造云端 MCU 身份，只要 SOC 能继续保证同流顺序即可。定义版本在同一 stream 内保持稳定，变更定义需换流并提供完整快照。

### 5.3 MQTT 通道与公共消息头

| 方向 | Topic | QoS / retain |
|---|---|---|
| SOC → 云 | snowpod/{region}/{deviceSn}/alarm/report | 1 / false |
| 云 → SOC 持久化接收回执 | snowpod/{region}/{deviceSn}/alarm/ack | 1 / false |

设备仅能发布自己的 report、订阅自己的 ack。云端以认证主体与 topic 绑定确定设备身份，JSON device_id 必须一致。认证失败不向攻击者发送带设备信息的业务回执。

JSON UTF-8，单条最大 256 KiB。禁止重复 JSON key。上行三种 type：alarm.single、alarm.snapshot、alarm.status。

| 公共字段 | 类型 / 规则 |
|---|---|
| v | 整数，固定 1；协议主版本，与字典版本无关 |
| type | 上述三种消息类型 |
| device_id | 设备 SN，必须与认证主题一致 |
| message_id | UUID，一条持久化消息一个；重试保持不变 |
| stream_id | UUID，上报流身份；同一流内序号不重置 |
| report_seq | 十进制字符串，1 起严格递增，最大 9223372036854775807 |
| ts | 首次生成消息的 UTC 毫秒，时钟未知为 0；重试不改 |
| data | 业务对象 |

序号统一用十进制字符串，避免 JavaScript 大整数精度损失；不带正号、空格或前导零，所有 report_seq 均从 "1" 起，不使用 "0" 作为快照序号。UINT32 detail 用 JSON 整数，云端数据库用 BIGINT，不能用 Java 有符号 int 截断。

同一消息重发时保持 message_id、stream_id、report_seq 及载荷不变。同一流内 report_seq 不复用；需要重置序号时必须使用不同 stream_id。

云端按 (device_id, message_id) 及 (device_id, stream_id, report_seq) 去重；同一身份不同内容视为冲突，不以最后一次覆盖。不同身份的相似事件被视为独立事件，SOC 必须保留原事件身份。

### 5.4 单报 alarm.single

```json
{
  "v": 1,
  "type": "alarm.single",
  "device_id": "SN-DEMO-001",
  "message_id": "c432a2f1-0a88-4ef0-a734-7b4e15b6a001",
  "stream_id": "e78c296d-312e-42d7-b7a4-8abf2418b001",
  "report_seq": "101",
  "ts": 1789704000000,
  "data": {
    "source_component": "main_mcu",
    "catalog_key": "main-mcu",
    "alarm_definition_version": "1.0.0",
    "observed_at": 1789704000000,
    "time_quality": "synced",
    "mcu_uptime_ms": "83000",
    "alarm_code": 1000,
    "severity": 3,
    "state_mask": 3,
    "clear_mode": 1,
    "detail": 0
  }
}
```

示例只演示格式，不宣称这些组合是某个真实故障的业务定义。

- source_component 本期固定 main_mcu；catalog_key 本期固定 main-mcu，不允许设备任意创建云端目录。
- observed_at 是 SOC 首次观察源消息的时间，时钟未知为 null；time_quality 为 synced/unsynced。ts 不是重试发送时间。
- mcu_uptime_ms 是源事件发生时的 MCU 启动内毫秒数字字符串，可缺省。不能用重传时刻替代。
- alarm_code 范围 0–65535，severity/state_mask/clear_mode 范围 0–255，detail 范围 0–4294967295。范围内未知枚举保留并标识，范围外拒绝。
- alarm_definition_version 可以缺省/null，使用云端明确配置的默认定义并标识。空字符串或不合法格式拒绝；合法但未知版本接收为未匹配。
- 同一 stream 内定义版本保持稳定；定义改变需换流并完整校准，不能让同一 code 在一个流中变义。
- detail=0 按 detail 字典的“无详细原因”语义展示。所有其他值先保留原数值；是否可按 code 解释，受§5.9待确认事项约束。

一次性 EVENT 使用同一结构，state_mask 的 bit2=1。例如 mask=4 即普通 EVENT；不需要额外发一个 NORMAL，也不创建待清除实例。

### 5.5 完整快照 alarm.snapshot

云端只接受一条消息表达的完整状态快照，不接收串口分片。何时采集和上报由设备团队决定；未取得有效完整快照时，云端不声明全量状态已同步。

```json
{
  "v": 1,
  "type": "alarm.snapshot",
  "device_id": "SN-DEMO-001",
  "message_id": "c432a2f1-0a88-4ef0-a734-7b4e15b6a002",
  "stream_id": "e78c296d-312e-42d7-b7a4-8abf2418b001",
  "report_seq": "102",
  "ts": 1789704001000,
  "data": {
    "source_component": "main_mcu",
    "catalog_key": "main-mcu",
    "alarm_definition_version": "1.0.0",
    "observed_at": 1789704001000,
    "time_quality": "synced",
    "coverage": "condition_slots_v1",
    "complete": true,
    "reported_count": 1,
    "highest_severity": 3,
    "entries": [
      {
        "alarm_code": 1000,
        "state_mask": 3,
        "severity": 3,
        "clear_mode": 1,
        "detail": 0,
        "metadata_origin": "single_report"
      }
    ]
  }
}
```

coverage=condition_slots_v1 覆盖 1000–1095、1100–1195、1200–1295、1300–1395，共 384 个位置；各组 xx96–xx99 不在范围内。entries 只列 active 或 latched 非零的 CONDITION；码唯一，不能超范围，bit2 必须为零，reported_count 必须等于 entries 长度（0–384）。空 entries 是合法的全范围正常快照。结构校验不通过时整份拒绝，不能部分应用。

metadata_origin 为 snapshot（快照中实际取得的完整元数据）、single_report（缓存）或 unknown。SOC 保证缓存来自当前有效状态对应的同一 code/定义；不能拿旧 MCU 会话的缓存解释新故障，无法证明时传 unknown。缓存只是最后已知值，不宣称快照时刻刷新。unknown 时 severity、clear_mode、detail 均为 null；本协议不再传元数据源序号。

highest_severity 是设备快照整体字段，只用于整体展示/诊断，不能填到每个 entries 的 severity。字典建议值与运行时元数据分别存储。

云端在一个事务中校准覆盖内所有码，包括没出现在 entries 的码；NORMAL 墓碑也保存快照 report_seq=W。同 stream 已有 report_seq 大于 W 的码不回退。覆盖内不大于 W 的迟到 CONDITION 单报仅补历史；EVENT 即使早于 W 也独立幂等入历史，快照不替代 EVENT。快照覆盖外（例如 1999）的合法单报不受该快照消警或水位过滤；这些码由自身 NORMAL 或流切换时的实例结束收敛。

### 5.6 状态与流切换恢复

alarm.status 使用§5.3公共头，data 格式如下：

```json
{
  "source_component": "main_mcu",
  "catalog_key": "main-mcu",
  "alarm_definition_version": "1.0.0",
  "mcu_link": "online",
  "lost_report_ranges": []
}
```

mcu_link 为 online/offline/unknown，仅表示 SOC 所见 MCU 链路情况；不以 SOC 连云推断 MCU 在线。不需要能力位或 MCU 身份字段，SOC 的完整性/顺序保证是对接前提。

lost_report_ranges 必填数组，无缺失时为 []，每个元素如 {"from":"90","to":"92"}，区间含两端，表示本 stream 中已知不可恢复的消息缺失。两端为正十进制字符串，from≤to，且 to 小于当前 status.report_seq。云端保留 history_gap，后续空列表不抹掉历史。快照 report_seq 大于已知缺失上界后可以恢复当前态，但不补造丢失 EVENT。

同流较旧 report_seq 的 status 不更新链路质量；同消息重传不刷新新鲜度。新鲜度以首次持久接收时间计算，默认阈值见工程配置，本文不规定 SOC 定时器。有效完整快照和 online 状态到齐后，且没有快照之后尚未处理/失败的状态消息，当前状态才可为 synced；未知/离线链路不宣称同步。

首条有效单报可以建立初始流并展示故障，取得完整快照前为 pending。后续新流的 status 或 snapshot 可以宣布切换；新流单报在旧流当前态尚未校准时等待完整快照，不使用新单报直接覆盖旧实例。新流快照结束旧流实例并建立基线；已经退休的流迟到 CONDITION 只补历史，EVENT 可幂等补历史，不重新接管当前态。无需额外绑定接口。

### 5.7 云端接收回执

MQTT PUBACK 只证明 MQTT 层接收，不证明云端业务数据库落盘。只有 alarm.receipt 的 accepted 表示云端已持久接收；未收到回执不能当作成功。

```json
{
  "v": 1,
  "type": "alarm.receipt",
  "device_id": "SN-DEMO-001",
  "ts": 1789704000200,
  "data": {
    "message_id": "c432a2f1-0a88-4ef0-a734-7b4e15b6a001",
    "stream_id": "e78c296d-312e-42d7-b7a4-8abf2418b001",
    "report_seq": "101",
    "result": "accepted",
    "code": "ACCEPTED",
    "warnings": []
  }
}
```

| result | 含义 | 对接处理 |
|---|---|---|
| accepted / ACCEPTED 或 DUPLICATE | 原始消息（含待处理状态）、幂等记录持久化完成；不保证投影已完成 | 核对 message_id/stream_id/report_seq，标记本次消息交付成功 |
| rejected / INVALID_PAYLOAD、IDENTITY_CONFLICT | 永久格式问题或身份冲突 | 未接收成功；修正数据或协议问题后处理，不作为成功回执 |

warnings 当前固定为空数组，保留作为可选扩展字段。未知字典/枚举、默认版本和元数据缺失在云端展示，不影响持久接收。数据库暂时失败时不发送 accepted；没有业务回执可原身份重发。

回执是逐条确认，无隐式累计确认。相同 message_id 或 stream+report_seq 内容冲突必拒绝。重传不更改 ts 或其他载荷；改变身份重新包装同一 MCU 事件时云端无法判定其重复。回执自身允许重复，SOC 幂等处理。

云端持久接收退休 SOC 流或旧序号快照后跳过当前态更新。accepted 的语义始终是持久接收，不承诺消息一定改变当前状态。拒绝记录、待处理状态和处理错误由云端保留。

### 5.8 云端处理保证与边界

- 同消息重复上报只产生一次业务效果；回执可以重复。
- 旧 ACTIVE 不能覆盖更新的 NORMAL；旧序号快照不能覆盖更晚单报。
- 完整快照只校准声明范围内的设备 CONDITION，不清除规则告警或 EVENT。
- SOC 流切换造成的实例结束标记 source_reinitialized；快照校准结束标记 snapshot_reconciled，不冒充精确 NORMAL 边沿。
- 快照可以恢复当前态，但不能补出遗漏的 EVENT。当前状态已同步与历史有缺口可以同时存在。
- accepted 后的处理失败由云端有限重试；耗尽后保留失败记录并由运维修复恢复，不要求设备生成新事件。
- 未确认消息可以原样重发；不规定设备缓存、发送顺序或退避实现。无法恢复的缺失以§5.6约定报告。

### 5.9 字典和固件的关系

固件版本独立作为设备信息报告，不参与告警字典选择。设备只报 alarm_definition_version，例如 1.2.0；云端维护该定义的字典 revision，例如 3，完整显示 1.2.0.3。第四段只适用于前三段完全相同的定义。

同固件可报告不同定义，不同固件也可报告同定义；前提是设备实际按所报告定义编码，不能只改版本标签。云端不下发字典给设备，不维护固件×字典兼容矩阵。

建议默认定义 1.0.0，须与首次正式设备定义核准后配置。缺省使用默认并标记；明确未知定义保留 raw 并显示未知，不能套默认。同一版本下码义不可改，云端文本修订发布为新的不可变 revision。

**必须冻结的业务差异：**用户希望 detail 全部是独立 detail code，但设备表部分描述电流值、故障位图等。设备方应确认是否全部转换为 code；若保留原始值，需按定义版本提供明确的 event code→detail 类型清单。确认前，这些歧义条目只展示原始值/语义待确认，不能偶然命中 detail 字典就展示错误原因。本方案不要求建立 event/detail 固定父子关系表。

### 5.10 云端查询与持久化字段边界

协议序号使用十进制字符串；内部存储为 BIGINT。detail 是 UINT32 数字码，不是诊断对象；云端解析后的字典名称、原因及原始元数据存入 `alarm_event.detail` JSONB，这个 JSONB 与上行数值 `data.detail` 不同。

| 云端字段 | 语义 |
|---|---|
| source | `device` / `rule`，两条来源独立 |
| identity_key | 设备值为 `main_mcu:main-mcu:{alarm_code}`；活动唯一键为 `(device_sn, source, identity_key)` |
| record_kind / life_state | 设备 `CONDITION` 对应 `ACTIVE` / `RTN_LATCHED` / `NORMAL`；设备 `EVENT` 对应 `EVENT` |
| status | 设备 CONDITION 未结束为 `active`，NORMAL 后 `cleared`；一次性 EVENT 为 `occurred`，不等待恢复、不走 TTL |
| dictionary_release_id | 接收时固定对应字典修订；未知定义为 null，后续云端字典切换不重新解释已接收消息 |
| default_version / dictionary_status / detail_status | 区分缺省版本、未知定义、未知码及未确认 detail，未知数据保留并标识 |
| condition_recovered_at | 已有实例从其他状态进入 RTN_LATCHED 时记录 observed_at；首次即 RTN_LATCHED 或无观察时间时可为空，不推断准确恢复时刻 |
| clear_reason / close_reason | 上报 NORMAL：`recovered`；快照校准：`snapshot_reconciled`；源会话替换：`source_reinitialized` |

V38 新增时间字段统一为 TIMESTAMP / LocalDateTime，运行时由 Java 显式赋值，没有数据库默认 NOW()。协议 `ts` / `observed_at` 仍为 Unix 毫秒；`observed_at` 落库按统一应用时区转换。已有 `alarm_event.first_ts/last_ts/cleared_at` 保留 TIMESTAMPTZ，显式写入带时区时间；time_quality=unsynced 或 observed_at 为空时，生命周期时间回退到首次云端接收时间。接收时间通过 JDBC `getObject("received_at", LocalDateTime.class)` 读取到 DTO，不依赖驱动隐式类型。

字典发布表、事件码表和 detail 码表按 release_id 逻辑关联，事件码与 detail 码之间没有直接父子外键；只在单报 detail 值解释时查独立 detail 字典。V41 移除 MCU 源身份列，当前态改用 stream_id/report_seq，并要求重新建立快照基线。V39 固定种子发布时间，后续导入由 Java 生成创建时间。当前 V39 种子包含 105 条事件码和 78 条 detail 码，完整内容见 [初始字典](../spec/alarm/dictionary-1.0.0.1.json)。全部关联由应用维护，不建立物理外键。云端人工 ACK 仅表示已读，不代表设备 NORMAL，也不触发 RESET。表与处理流程详见 [告警工程文档](../spec/alarm/README.md)。

`reason`（cancel）：`user` / `system` / `error`。

|------|------|------|------|
| `stream_type` | string | 是 | `live`（实时）或 `recording`（录像回放）|

设备收到每条指令后，必须在 `cmd/ack` topic 回复。同样遵循 §2 封套结构，`req_id` 回传封套层的原值，`data` 含应答业务字段：

```json
    "detail": {}
  }
}
```

`result` 枚举：`accepted` / `rejected` / `error`

`reason`（`result=rejected` 时必填）枚举：

| reason | 说明 |
|--------|------|
| `invalid_state` | 当前 mode/substate 不允许此指令 |
| `door_open` | 外门未关闭 |
| `estop_active` | 急停触发中 |
| `o2_not_ready` | 氧含量未达目标阈值 |
| `powder_empty` | 粉料为空 |
| `job_not_found` | `model_ref` 无法获取 |
| `safety_interlock` | 安全联锁阻止 |
| `already_in_progress` | 已有进行中的作业 |
| `pm25_too_high` | PM2.5 超标，拒绝解锁 |
| `sensor_fault` | 关键传感器故障，拒绝执行 |
| `push_already_active` | 该 `stream_type` 已有推流进行中（先发 `stop_rtsp_push`）|
| `recording_not_found` | 指定 `recording_id` 的录像文件不存在 |
| `encoder_error` | 编码器或推流进程启动失败 |
| `job_file_error` | 作业文件下载失败或 SHA256 不匹配 |
| `powder_insufficient` | 粉料估算不足以完成作业（重量不达标）|
| `filter_required` | 滤芯严重超限，必须更换才可打印 |
| `galvo_not_calibrated` | 振镜未完成校准或校准已过期 |
| `model_incompatible` | 模型文件格式或参数与当前固件版本不兼容 |

## 八、OTA 消息

### 8.1 版本通知（`ota/notify` 下行，含 §二 封套）

```json
{
  "v": 1,
  "type": "ota_notify",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "data": {
    "task_id": "ota-20260805-0001",
    "firmware_type": "soc",
    "version": "1.3.0",
    "url": "SNOWPOD-X1/1.3.0.bin",
    "sha256": "a1b2c3d4...",
    "size_bytes": 8388608,
    "required": false,
    "release_notes": "修复振镜校准稳定性问题"
  }
}
```

`firmware_type`：`soc` / `mcu` / `galvo`。`required=true` 表示强制升级，设备须在当前作业完成后执行（云端仅标记，设备端执行前仍须确认 + 完整性校验，签名校验待 v0.10 定义）。

`url`：**相对路径**（`{productModel}/{version}.{ext}`，不含 host/scheme），与固件存储实现一致（`LocalFirmwareStorage` 返回相对路径入库）。设备端下载地址 = `downloadBaseUrl`（受信下载根，仅 HTTPS + 受信 host）按 **RFC 3986 相对解析规则** resolve 该 url，不得裸字符串拼接。**`downloadBaseUrl` 的传输机制（下发通道/配置键）当前未定义，待 v0.10 补全**；定义时须钉死：唯一来源、必须 HTTPS + host 白名单、尾部 `/` 规范（RFC 3986 §5.3 下 base 尾斜杠改变解析结果，给规范值而非规则）、配置缺失/非法时拒绝下载。

> **签名校验注记（2026-08-06）**：强制升级的固件签名校验是设计要求，但签名算法/编码/签名对象/信任根/keyId 轮换/失败行为尚未在本协议定义（待 v0.10）。当前阶段设备端以 **SHA-256 完整性校验**（`sha256` 字段）为准。

`task_id`：OTA 任务关联键，由云端建任务时分配。一个任务对多台设备时各台收到的 `task_id` 相同（一对多）；设备须在 `ota_progress` 中原样带回（§8.2），云端按 `(task_id, device_id)` 反查任务行。与封套 `req_id`（一对一请求-应答）职责不同，`task_id` 不复用 `req_id` 槽位。

### 8.2 进度上报（`ota/progress` 上行，含 §二 封套）

```json
{
  "v": 1,
  "type": "ota_progress",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "data": {
    "task_id": "ota-20260805-0001",
    "firmware_type": "soc",
    "state": "downloading",
    "progress_pct": 45,
    "error_code": null
  }
}
```

`state`：`downloading` / `verifying` / `applying` / `completed` / `failed` / `rolled_back`。

`task_id`：设备将收到 `ota_notify` 时的 `data.task_id` 原样带回（见 §8.1）。云端按 `(task_id, device_id)` 定位该台设备的任务行（ota_task_device）。封套 `req_id` 不承担任务关联（一对多业务身份走 `task_id`，一对一请求关联走 `req_id`）。终证据不依赖 progress 的 `completed`：completed 仅表示设备自认刷完，真终证据是重启后心跳（§8.3）回带目标 `firmware_type` 的 `version` == 任务快照 target。

### 8.3 心跳（`heartbeat` 上行，含 §二 封套）

设备周期上报自身版本与能力状态。默认周期 30 分钟（可配），上线时也发一次。topic：`snowpod/{region}/{device_id}/heartbeat`（QoS 1）。

```json
{
  "v": 3,
  "type": "heartbeat",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "boot_id": "b8f3a1c2-...",
  "data": {
    "uptime_s": 86400,
    "release_version": "2.3.0",
    "firmwares": [
      { "firmware_type": "soc", "version": "2.2.5" },
      { "firmware_type": "mcu", "version": "1.0.3" }
    ],
    "battery": 87,
    "network": { "type": "wifi", "rssi": -58 }
  }
}
```

| 字段 | 层级 | 类型 | 说明 |
|------|------|------|------|
| `v` | 封套 | int | 心跳 schema 版本，当前 `3`（演进见下方表） |
| `boot_id` | 封套 | string | 设备本次启动唯一 ID，每次重启重新生成；配合 `seq` 做乱序门闩（重启后 seq 可归零，`boot_id` 变化即重启，用 `ts` 兜底）。**v2 起从 `data` 迁到封套顶层** |
| `data.release_version` | data | string\|null | **整机版本号**（= Release 版本，复用 `release_version` 命名空间，与 §8.4 的 `next_release_version` 同级），心跳 v3 新增，check-update 的版本对账锚。**只允许 null 或非空串，缺键/空串/纯空白一律按未上报** |
| `data.uptime_s` | data | int | 本次启动后运行秒数 |
| `data.firmwares` | data | array | 各固件版本清单 `[{firmware_type, version}]`，`firmware_type` 枚举 soc/mcu/galvo |
| `data.battery` | data | int\|null | 电量百分比（强制升级能力检查用） |
| `data.network` | data | object | 网络摘要 `{type, rssi}`（升级下载能力检查用） |

**心跳 schema 版本演进（封套 `v` 字段）**：

| `v` | 变化 |
|---|---|
| `1` | `boot_id` 在 `data` 内 |
| `2` | `boot_id` 迁到封套顶层（`envelope.boot_id`） |
| `3` | `data` 顶层新增 `release_version`（整机版本号） |

云端消费端 v1/v2/v3 双读兼容（迁移窗口）；新固件按 `v=3` 发，才能让 `release_version` 生效、check-update（§8.4）可用。

**release_version 空口径**：入库 `device_ota_status.release_version`，DB 级硬约束「只能 null 或非空串」（`IS NULL OR btrim(release_version) <> ''`）。设备上报语义化数字版本号（缺段补 0 逐段比较，同 §8.4 对账口径）；无版本能力时不带该字段或填 null。空串、纯空白、缺键统一按未上报归 null，不允许给 `""` 留第二种「空」定义。

- 封套 `req_id` 可选（心跳非请求-应答）。身份与 model 以 MQTT 认证身份 + device 注册表为准，不信 payload。
- 云端消费：心跳更新 `device_ota_status`（按 `firmware_type` 存版本 + `release_version` 存整机版本 + `last_reported_at/last_boot_id/last_seq`，`boot_id+seq` 单调门闩）；终证据对账走目标 `firmware_type` 的 version 与任务快照对比。
- setup_emqx.py 同步加规则 `iot_device_heartbeat`：`snowpod/+/+/heartbeat` → Kafka `iot.device.heartbeat`。

### 8.4 检查更新（`ota/check` 上行 + `ota/check_ack` 下行，pull 模型）

设备主动拉取可升级版本，与定向推送 `ota/notify`（§8.1）互补。设备上行 `ota/check` 请求（EMQX 规则 `iot_device_ota_check` 写入 Kafka `iot.device.ota_check`），云端计算后下行 `ota/check_ack` 应答（EMQX HTTP publish 直发，不经 Kafka）。

**请求（`ota/check` 上行，含 §二 封套，QoS 1）**：

```json
{
  "v": 1,
  "type": "ota_check",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "req_id": "7f3a1b2c-...",
  "data": {}
}
```

`data` 恒为空。版本对账锚为服务端 `device_ota_status.release_version`（心跳上报 §8.3），不采纳设备自报版本。

**应答（`ota/check_ack` 下行，含 §二 封套，QoS 1）——有更新**：

```json
{
  "v": 1,
  "type": "ota_check_ack",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12346,
  "req_id": "7f3a1b2c-...",
  "data": {
    "next_release_version": "1.5.0",
    "components": [
      { "component": "soc", "version": "2.3.0", "url": "https://...", "size_bytes": 1048576, "sha256": "abcd..." }
    ]
  }
}
```

**应答（`ota/check_ack` 下行）——已最新 / 未就绪重试**（`error` 封套，`data` 为 null）：

```json
{
  "v": 1,
  "type": "ota_check_ack",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12346,
  "req_id": "7f3a1b2c-...",
  "error": { "code": "OTA_NO_UPDATE", "message": "no update available" }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `req_id` | string | 请求关联键，应答原样带回 |
| `data.next_release_version` | string\|null | 下一步整机版本号（必经优先），仅「有更新」态 |
| `data.components` | array\|null | 差量组件清单（已到位组件不出现），元素 `{component, version, url, size_bytes, sha256}` |
| `data.components[].url` | string | 预签名下载 URL（完整地址，含临时签名） |
| `error.code` | string | `OTA_NO_UPDATE`（已最新）/ `OTA_VERSION_NOT_READY`（整机版本未落库，稍后重试） |
| `error.message` | string | 人类可读描述 |

三态：有更新（`data` 携带）/ 已最新（`OTA_NO_UPDATE`）/ 未就绪重试（`OTA_VERSION_NOT_READY`）。

## 九、流信令消息（摄像头）

**架构说明**：视频/录像全存设备端，不上云。信令走 MQTT（`cmd` / `cmd/ack`），媒体流走 RTSP over TCP。云侧部署 **mediamtx** 作为 RTSP Broker；设备主动推流（RTSP ANNOUNCE），App 从 Broker 拉流（RTSP PLAY）。

```
【走云端接口时（固定 relay 路径）】
① App  ─────────────────────→ Cloud API: 请求开流
② Cloud ────(MQTT cmd)──────→ Device: start_rtsp_push（push_url + push_token）（fire-and-forget）
③ Device ──RTSP ANNOUNCE──→ mediamtx relay（出站 TCP，穿透 NAT）
④ App  ────RTSP PLAY─────────→ mediamtx relay（cloud API 下发 pull_url + pull_token）
```

> **局域网直连**：App 在调用云端接口前可自行判断与设备是否同局域网；若可通则直接与设备 RTSP 端口通信，不调用云端接口，云端不介入此路径。

**relay 路径规则：**

| stream_type | push_url / pull_url 路径格式 |
|-------------|------------------------------|
| `live` | `/live/{device_id}` |
| `recording` | `/rec/{device_id}/{recording_id}` |

**`cmd/ack` 中 `detail` 字段补充说明：**

`snapshot` 应答的 `detail`：

```json
{ "snapshot_data": "/9j/4AAQSkZJR...", "captured_at": 1753228800000 }
```

`captured_at`：快照实际拍摄时刻（毫秒），与封套 `ts`（ack 发出时刻）因编码耗时略有差值，与 `push_started_at` 命名风格保持一致。

`start_rtsp_push` 应答的 `detail`：

```json
{ "push_started_at": 1753228800000 }
```

## 十、打印流程消息时序

本节保留既有作业事件示例，其字符串 code 与对象 detail 属于作业链路，不是 §五 的 MCU 告警码字典。打印状态仍通过 state 上报；设备故障另走 alarm/report。

完整打印作业从下发指令到取件完成的端到端消息序列，对应协议骨架 §6 状态机。

### 10.1 正常流程

```
Cloud/App                         Device（SoC）

─── 1. 发起打印 ───────────────────────────────────────────
→ cmd: start_print
  { job_id, model_ref, model_sha256, total_layers, ... }

← cmd/ack: accepted
  （快速前置检查通过：门关、急停正常、O₂传感器有效、
    安全联锁正常；文件未下载——异步进行）

← state: { mode=idle, substate=job_loading, job.job_id=... }
  （开始下载并校验模型文件）

─── 2. 洗气（Purge）─────────────────────────────────────
← state: { mode=purge, substate=checking_door }
← state: { mode=purge, substate=purging_o2,
            job.layer=0, job.total_layers=500 }
  （telemetry/chamber 中 o2_ppm 逐渐下降，App 监控此值）
← state: { mode=purge, substate=stabilizing }
← event: PURGE_COMPLETE { o2_ppm: 7800, target_ppm: 8000 }

─── 3. 加热 + 回零（Heating + Homing）──────────────────
← state: { mode=printing, substate=heating }
← state: { mode=printing, substate=homing }

─── 4. 逐层打印（Layer Loop）────────────────────────────
← state: { mode=printing, substate=layer_printing,
            job.layer=1, job.total_layers=500,
            job.progress_pct=0, job.eta_s=14000 }
  （每完成 N 层或固定间隔更新一次 state，不要求每层一条）

  ... 打印中 telemetry 持续上行（chamber 1-2s，dust 5s）...

← state: { mode=printing, substate=layer_printing,
            job.layer=250, job.progress_pct=50, job.eta_s=7000 }

─── 5. 暂停/恢复（可选）────────────────────────────────
→ cmd: pause
← cmd/ack: accepted
← state: { mode=printing, substate=pausing }
← state: { mode=printing, substate=paused }
  （既有作业暂停通知：event PRINT_PAUSED active=true；不创建 MCU 告警）

→ cmd: resume
← cmd/ack: accepted
← state: { mode=printing, substate=layer_printing, ... }
  （既有作业恢复通知：event PRINT_PAUSED active=false；不用于 MCU 消警）

─── 6. 打印完成 + 冷却 ──────────────────────────────────
← state: { mode=printing, substate=cooling,
            job.layer=500, job.progress_pct=100, job.eta_s=0 }
← event: PRINT_COMPLETE
  { job_id: "job-20260723-001", total_layers: 500, duration_s: 14400 }

─── 7. 取件（Unload）────────────────────────────────────
← state: { mode=unload, substate=dust_extracting }
  （除尘系统启动，telemetry/chamber pm25 开始下降）
← state: { mode=unload, substate=waiting_pm25 }
← state: { mode=unload, substate=unlock_allowed }
  （PM2.5 已降至 pm25_threshold_ugm3 以下，联锁满足）

→ cmd: request_unlock
← cmd/ack: accepted
← state: { mode=unload, substate=unloading }
  （外门解锁，用户取出零件）

← state: { mode=idle, substate=ready, job=null }
  （取件完成，设备回到待机）
```

### 10.2 start_print 被拒绝（快速前置检查失败）

```
→ cmd: start_print { ... }
← cmd/ack: rejected, reason=door_open
  （或 estop_active / powder_empty / sensor_fault /
     filter_required / galvo_not_calibrated 等）
  （state 保持 idle/not_ready 不变）
```

### 10.3 作业文件下载失败（ack 接受后异步失败）

```
→ cmd: start_print
← cmd/ack: accepted
← state: { mode=idle, substate=job_loading }
← event: JOB_FILE_ERR
  { job_id: "...", reason: "sha256_mismatch" }
← state: { mode=idle, substate=not_ready, job=null }
  （设备回到初始状态，需重新下发）
```

### 10.4 打印中途取消

```
→ cmd: cancel { reason: "user" }
← cmd/ack: accepted
← state: { mode=printing, substate=cooling }
  （安全冷却后进入 unload）
← state: { mode=unload, substate=dust_extracting }
  ... （同正常取件流程）
← state: { mode=idle, substate=ready }
```

### 10.5 打印中发生错误

```
← alarm/report: alarm.single { alarm_code: <设备字典中的运动故障码>, state_mask: 1, ... }
  （此行为时序示意；完整 JSON 和数字码字段见 §5.4，不使用 MOTION_STALLGUARD 字符串码）
← state: { mode=printing, substate=paused }
  （设备自动暂停，等待用户决策）

  [ 用户恢复 ]
→ cmd: resume
← cmd/ack: accepted / rejected

  [ 或用户取消 ]
→ cmd: cancel { reason: "error" }
← cmd/ack: accepted
  ... （进入冷却/unload 流程）
```

## 十一、后端 Kafka Topic 数据结构

EMQX Rule Engine 将设备上行消息路由至对应 Kafka Topic，以下为各 topic 的 payload 格式。

### 11.1 `iot.device.error` — 既有错误事件路由（非告警入口）

由 EMQX 消费设备 `event` topic（`snowpod/{region}/{device_id}/event`）后路由写入，触发条件为字符串 severity 等于 error、critical 或 emergency。此路由仍在基础设施规则清单中，但 `iot-alarm` 已不消费；不能用它接入 §五 设备主动告警。

```json
{
  "v": 1,
  "type": "event",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12346,
  "data": {
    "code": "MOTION_STALLGUARD",
    "severity": "error",
    "active": true,
    "ts": 1753228800000,
    "detail": { "axis": "z1", "raw": 45 }
  }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `v` | int | schema 版本 |
| `type` | string | 固定 `event` |
| `device_id` | string | 设备唯一 ID |
| `ts` | int64 | 消息产生时刻（毫秒时间戳） |
| `seq` | uint32 | 设备端单调序号，用于去重 |
| `data.code` | string | 既有业务事件码，与 §五 MCU 数字码无映射关系 |
| `data.severity` | string | `info` / `error` / `critical` / `emergency` |
| `data.active` | bool | true=触发，false=恢复 |
| `data.ts` | int64 | 告警**实际**触发/恢复时刻（毫秒）；与封套 `ts`（消息发出时刻）可能不同，消费方应以此字段作为告警时间线依据 |
| `data.detail` | object | 辅助诊断数据，随 code 不同而异，可为空对象 |

> 本节记录既有路由格式，不承诺告警实例或错误日统计已由该 topic 生成。设备告警入口见 §11.11；遥测规则入口见 §十二。

### 11.2 `iot.device.status` — 设备连接状态变更

由 EMQX 连接/断开事件路由写入。

```json
{
  "device_id": "SNOWPOD-A1B2C3D4",
  "event": "client.connected",
  "peername": "192.168.1.50:58372",
  "ts": 1753228800000
}
```

| 字段 | 说明 |
|------|------|
| `device_id` | 设备唯一 ID，取自 EMQX `clientid`，与 §二 封套字段含义一致 |
| `event` | `client.connected`（上线）/ `client.disconnected`（下线）|
| `peername` | 设备来源对端地址，取自 EMQX `peername`（IP:PORT），拆纯 IP 写 `device_status.ip`（上线写、下线保留）|
| `ts` | EMQX Broker 时间，用于写 `device_status.last_online_time` / `last_offline_time` |

### 11.3 `iot.device.state` — 设备状态变更

由 EMQX 消费设备 `state` topic 后透传写入，mode 或 substate 发生变化时触发。

```json
{
  "v": 1,
  "type": "state",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12345,
  "data": {
    "mode": "printing",
    "substate": "layer_printing",
    "since": 1753228800000,
    "job": {
      "job_id": "job-20260723-001",
      "layer": 42,
      "total_layers": 500,
      "progress_pct": 8,
      "eta_s": 14000,
      "started_at": 1753228800000
    },
    "health": {
      "laser":  "ok",
      "galvo":  "ok",
      "motion": "ok",
      "dust":   "ok",
      "safety": "ok"
    }
  }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `v` | int | schema 版本 |
| `type` | string | 固定 `state` |
| `device_id` | string | 设备唯一 ID |
| `ts` | int64 | 消息产生时刻（毫秒时间戳） |
| `seq` | uint32 | 设备端单调序号，用于去重 |
| `data.mode` | string | 设备当前主模式，枚举见§四 |
| `data.substate` | string | 当前子状态，枚举见§四 |
| `data.since` | int64 | 进入当前 mode 的时间戳（毫秒） |
| `data.job` | object\|null | 仅 purge/printing/unload 时携带，其余为 null |
| `data.health` | object | 各子系统健康状态，`ok`/`warn`/`fault` |

> **消费方**：`iot-device-manager`（写设备状态表）、`iot-data-process`（跟踪作业进度）、推送服务（App实时状态同步）

### 11.4 `iot.device.event` — 设备事件（全量）

由 EMQX 消费设备 `event` topic 全量写入（含 info/error/critical/emergency 所有级别）。与 `iot.device.error` 并行路由。当前 `iot-device-manager` 将此 topic 追加到 device_event；`iot-alarm` 不从这两个 topic 创建设备告警。

```json
{
  "v": 1,
  "type": "event",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12346,
  "data": {
    "code": "PRINT_COMPLETE",
    "severity": "info",
    "active": true,
    "ts": 1753228800000,
    "detail": {
      "job_id": "job-20260723-001",
      "total_layers": 500,
      "duration_s": 14400
    }
  }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `v` | int | schema 版本 |
| `type` | string | 固定 `event` |
| `device_id` | string | 设备唯一 ID |
| `ts` | int64 | 消息产生时刻（毫秒时间戳） |
| `seq` | uint32 | 设备端单调序号 |
| `data.code` | string | 既有作业/通用事件码，如 PRINT_COMPLETE；不引用 §五 设备告警字典 |
| `data.severity` | string | `info` / `error` / `critical` / `emergency` |
| `data.active` | bool | true=触发，false=恢复 |
| `data.ts` | int64 | 事件**实际**发生时刻（毫秒）；与封套 `ts`（消息发出时刻）可能不同 |
| `data.detail` | object | 辅助诊断数据，随 code 不同而异 |

> **已实现消费方**：`iot-device-manager`（追加 device_event）。作业处理或 App 推送须按对应服务实现另行核验，本次 alarm 改造不据此宣称已实现。

### 11.5 `iot.device.cmd_ack` — 指令应答

由 EMQX 消费设备 `cmd/ack` topic 后写入。

```json
{
  "v": 1,
  "type": "command_ack",
  "device_id": "SNOWPOD-A1B2C3D4",
  "ts": 1753228800000,
  "seq": 12346,
  "req_id": "7f3a1b2c4d5e6f7a8b9c0d1e2f3a4b5c",
  "data": {
    "cmd": "start_print",
    "result": "accepted",
    "reason": null,
    "detail": {}
  }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `v` | int | schema 版本 |
| `type` | string | 固定 `command_ack` |
| `device_id` | string | 设备唯一 ID |
| `ts` | int64 | 应答产生时刻（毫秒时间戳） |
| `seq` | uint32 | 设备端单调序号 |
| `req_id` | string | 与下发指令中 `req_id` 一致，用于关联 |
| `data.cmd` | string | 被应答的指令名 |
| `data.result` | string | `accepted` / `rejected` / `error` |
| `data.reason` | string\|null | result=rejected 时必填，枚举见§七 |
| `data.detail` | object | 附加数据（如 snapshot 的 base64、set_config 实际生效值） |

> **消费方**：`iot-command-downlink`（通过 reqId 关联应答，处理超时/重试）、审计日志

| 字段 | 类型 | 说明 |

```json
    "stream_id": "e78c296d-312e-42d7-b7a4-8abf2418b001",
    "report_seq": "101",
    "ts": 1789704000000,
    "data": {
      "source_component": "main_mcu",
      "catalog_key": "main-mcu",
      "alarm_definition_version": "1.0.0",
      "observed_at": 1789704000000,
      "time_quality": "synced",
      "mcu_uptime_ms": "83000",
      "alarm_code": 1000,
      "severity": 3,
      "state_mask": 3,
      "clear_mode": 1,
      "detail": 0
    }
  },
  "topic": "snowpod/cn/SN-DEMO-001/alarm/report",
  "username": "SN-DEMO-001",
  "clientid": "SN-DEMO-001",
  "timestamp": 1789704000010
}
```

| 字段 | 来源及含义 |
|---|---|
| payload | 完整 §五 报文；桥接为 JSON 对象或原始 JSON 字符串时消费者均可解析，不拆出 data 代替完整消息 |
| topic | broker 原始 MQTT topic，用于绑定 region 和设备 SN |
| username | broker 已认证主体，必须等于 topic 中设备 SN 及 payload.device_id |
| clientid | broker MQTT client ID，保留用于诊断，身份校验使用 username/topic |
| timestamp | broker 接收时间；不是设备 observed_at，也不代替数据库首次接收时间 |

EMQX SELECT `payload, topic, username, clientid, timestamp`，message value 为 `${.}`。以上认证字段必须来自可信 broker，不能从设备 JSON 中采信。消费方 `DeviceAlarmConsumer` 先持久接收消息/拒绝记录及回执 Outbox，再确认 Kafka 位点；accepted 不代表告警投影已完成。

### 11.12 `iot.alarm.event` — 云端生成的告警通知

本 topic 由云端生成，不是 MQTT 原始上报。以下只定义本次设备来源的消息；现有规则来源通知不因此统一成这份结构。

| 字段 | 类型 | 设备来源语义 |
|---|---|---|
| notification_id | string | `device:{消息表主键}:{alarm_code}`，消费方幂等键 |
| deviceSn | string | 设备 SN；Kafka key 同设备 SN |
| source | string | `device` |
| recordKind | string | CONDITION / EVENT |
| lifeState | string | ACTIVE / RTN_LATCHED / NORMAL / EVENT |
| alarmId | int64 | alarm_event 实例主键 |
| severity | string | info / warning / error / critical / unknown |
| isHistorical | boolean | 快照、历史补录或迟到数据标记，通知方据此区分实时提醒 |
| detail | object | 原始数字字段及云端字典解析信息，包含 effective_version、default_version、dictionary_status 等；不是上行数值 detail 本身 |

设备 EVENT 或实例状态变化时写入 Outbox；发送可能重复，消费方按 notification_id 去重。本次只产生 Kafka 通知，不代表已实现 App 推送。回执走 MQTT alarm/ack，不从本 topic 返回。

### 11.13 告警死信数据

| Topic | 原消息来源 | 数据结构 |
|---|---|---|
| iot.device.alarm.report.dlt | iot.device.alarm.report | 保留 §11.11 原始 Kafka key/value，含 broker 元数据 |
| iot.alarm.telemetry.dlt | iot.device.telemetry.* | 保留原遥测 Kafka key/value |

死信由云端错误处理器产生，源 topic/partition/offset 与异常信息在 Kafka headers 中，不另造 MQTT/JSON 封套。写入对应原分区，DLT 分区数不得少于源 topic。有限重试耗尽后进入 DLT；确定性遥测配置/格式异常直接进入遥测 DLT。必须收到 DLT 发送确认后才提交原位点，失败停止对应消费。业务格式拒绝可持久化拒绝记录并返回 rejected，不等同于基础设施处理失败进入 DLT。回放必须保留设备消息身份及原始 broker 元数据，不能通过改序号制造新事件。

## 十二、遥测 Kafka Topic 数据结构

告警规则只提取 data 中顶层 JSON 数值字段，忽略布尔值、嵌套对象及 group；下列业务场景描述不表示所有示例字段都已配置规则。规则告警使用 source=rule，与 §五 设备字典及快照独立。

遥测消息按 group 拆分为独立 Kafka topic，各 topic partition 数量按采样频率独立配置。全部由 EMQX Rule Engine 从 `snowpod/{region}/{device_id}/telemetry/{group}` 路由写入。

**Kafka Key**：统一为 `{device_id}`，保证同一设备的遥测消息有序落入同一 partition。

## 十三、Kafka Topic 汇总

| Kafka Topic | 来源 MQTT Topic | 触发条件 | 主要消费方 |
|-------------|----------------|---------|-----------|
| `iot.device.alarm.report` | `alarm/report` | single / snapshot / status 全量 | iot-alarm（设备主动告警） |
| `iot.device.error` | `event` | 既有 severity 过滤路由 | 非 iot-alarm 入口，见 §11.1 |
| `iot.device.status` | EMQX 连接事件 | 上线/下线 | iot-device-manager |
| `iot.device.state` | `state` | mode/substate 变化 | iot-device-manager, iot-data-process, 推送服务 |
| `iot.device.event` | `event` | 既有通用事件全量 | iot-device-manager（device_event） |
| `iot.device.cmd_ack` | `cmd/ack` | 全量 | iot-command-downlink, 审计日志 |
| `iot.device.recording_list_response` | `recording/list_response` | 全量（录像列表请求应答） | iot-command-downlink |
| `iot.device.ota` | `ota/progress` | 全量 | iot-ota-service |
| `iot.device.ota_manifest_request` | `ota/manifest/request` | 全量（设备请求 manifest） | iot-ota-service |
| `iot.device.ota_check` | `ota/check` | 全量（设备检查更新，pull 模型） | iot-ota-service |
| `iot.device.heartbeat` | `heartbeat` | 全量（默认 30min + 上线即发） | iot-device-manager, iot-ota-service |
| `iot.device.telemetry.chamber` | `telemetry/chamber` | 1–2s（打印中） | iot-device-manager, iot-alarm |
| `iot.device.telemetry.chamber_ext` | `telemetry/chamber_ext` | 5–10s | iot-device-manager |
| `iot.device.telemetry.dust` | `telemetry/dust` | 5s | iot-device-manager, iot-alarm |
| `iot.device.telemetry.safety` | `telemetry/safety` | 5s + 事件 | iot-alarm, 审计日志 |
| `iot.device.telemetry.motion` | `telemetry/motion` | 按层/事件 | iot-device-manager, iot-alarm |
| `iot.device.telemetry.powder` | `telemetry/powder` | 30s + 事件 | iot-device-manager, iot-data-process, iot-alarm |
| `iot.device.telemetry.door` | `telemetry/door` | 事件驱动 | iot-alarm, iot-device-manager |
| `iot.device.telemetry.power` | `telemetry/power` | 10s | iot-device-manager, iot-alarm |

云端内部另有 `iot.alarm.event`、`iot.device.alarm.report.dlt`、`iot.alarm.telemetry.dlt`，格式见 §11.12–§11.13，不属于设备直发 MQTT 路由。

> **本表范围**：仅列「设备上行 → Kafka」的 topic（经 EMQX Kafka rule 路由）。设备下行 topic（云端 → 设备）不经 Kafka，由云端 EMQX HTTP publish 直发、无 Kafka rule：`alarm/ack`（告警接收回执）、`cmd`（指令）、`ota/notify`（版本通知）、`ota/manifest`（manifest 响应）、`recording/list_request`（录像列表请求）。

> **字段命名约定**：一般路由的 Kafka value 即设备上行 MQTT 消息的原始 payload（§二 封套，snake_case），EMQX Rule Engine 通过 `${payload}` 透传，消费方直接解析设备协议格式。告警专用 `iot.device.alarm.report` 是例外，使用 §11.11 的 broker 元数据封套，不能直接按设备报文根节点解析。注：`iot.device.status` 来自 EMQX 内置连接事件（非设备 MQTT 消息），payload 仅含 `device_id` / `event` / `peername` / `ts` 四字段，无 §二 封套结构，见 §十一.2。
